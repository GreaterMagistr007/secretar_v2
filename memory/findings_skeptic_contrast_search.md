### ВАЖНО-3. Тест «по наименьшему токену» правило наименьшего токена не закрепляет
src/lib/tasks/memory-repository.test.ts, тест «задачу с двумя токенами на префикс ставит по наименьшему и отдаёт один раз» (+864…+891 в диффе); docs/mechanic_tasks.md:85 — «задача с двумя токенами на один префикс (ставится по наименьшему и отдаётся один раз, как после `distinct()`)».
Проверил вручную на данных теста две мутации ключа в memory-repository.ts:
- «первый по счёту токен с префиксом»: both→молоко, lightning→молния, ground→молотый, порядок молния < молоко < молотый, при limit 2 выходит {lightning, both};
- «наибольший токен с префиксом»: both→молоко, lightning→молотый, ground→молотый, при limit 2 выходит {both, lightning}.
После sortTasksByDate обе мутации дают тот же [lightning, both], и `all` с limit 10 тоже совпадает. Ни одна мутация тест не роняет. Против старой реализации тест работает (там [lightning, ground]), но ключевое правило `.reduce((least, token) => (token < least ? token : least))` им не проверяется. Покрытие 100 % этого не показывает: строка исполняется, но результат не проверяется.
Предложение: добавить к тесту `search('мол', 1)` — тогда правило наименьшего даёт [both], правило первого токена даёт [lightning]. Для мутации «наибольший» нужен случай, где наибольший токен задачи выводит её за лимит: например, у задачи токены «молитва» и «молоток» против задачи с «молния» при limit 1.

## Проверено и в порядке
- **Семантика Dexie 4.4.6** (по node_modules/dexie/dist/dexie.mjs, а не по памяти):
  - `startsWith` = `between(str, str + '￿', true, true)` (стр. 2744-2747). Токен не может содержать U+FFFF (не \p{L}/\p{N}), поэтому диапазон равен `token.startsWith(indexKey)`.
  - `distinct()` (стр. 2339) у multiEntry-индекса добавляет фильтр по `primaryKey`: первое вхождение задачи — её наименьший ключ в диапазоне.
  - `addFilter` соединяет фильтры через `combine` в порядке вызова, `iter` (стр. 2020) ставит `replayFilter` (limit) после `ctx.filter`. Значит limit считает только строки, прошедшие distinct и filter.
  - Distinct отмечает задачу до filter, но filter зависит только от задачи, а не от строки индекса, поэтому расхождения нет.
  - Курсор multiEntry упорядочен по (ключ индекса, primaryKey). Сравнение строк в IndexedDB и `<` в JS — по кодовым единицам UTF-16, порядок одинаковый.
- **Модель в памяти этому эквивалентна:**
  - ключ — наименьший токен с префиксом (`reduce` без начального значения не падает: matchesSearchQuery гарантирует, что у задачи есть токен с префиксом каждого токена запроса, включая indexKey);
  - сортировка (key, id) с уникальными id;
  - `slice(0, limit)`, затем `sortTasksByDate`.
- **Пограничные случаи:**
  - пустой запрос и запрос из одних разделителей → tokens=[] → [] в обеих реализациях;
  - limit ≤ 0 → [] в обеих;
  - limit NaN: Dexie получает `--NaN`, фильтр отвечает false, итог []; память даёт `slice(0, NaN)` = [];
  - дробный limit: обе отдают floor;
  - Infinity: обе отдают всё;
  - ё/е нормализуются до индекса в обеих;
  - дубли токенов убирает tokenize, IndexedDB multiEntry их тоже схлопывает.
- **Остальные тесты:**
  - пять из шести новых тестов падают на прежней реализации «отсортировать, потом обрезать», это проверено пересчётом данных каждого теста; «ровно limit» проходит и на ней, документ так и пишет;
  - числа в ожиданиях тестов 1, 2, 3, 5, 6 пересчитаны вручную и верны;
  - тесты 5 и 6 отличают обход по длинному токену от обхода по короткому.
