# Замеры скорости голосовой команды на хосте (агент-исследователь, 2026-11-22)
Задача: повторить запрос телефона в `litert-lm-api` на CPU хоста, разложить время, сравнить рычаги ускорения, собрать опубликованные цифры, ранжировать меры. Код приложения и `docs/` не трогаются. Записи владельца не выгружаются.

## 0. Исходные данные (из `memory/tmp_voicelog_20261122/raw/voice-log.jsonl`)
- Хост: 16 потоков CPU, 62 ГБ ОЗУ.
- Телефон: backend GPU, audioBackend CPU, maxNumTokens 4096, maxOutputTokens 128, сэмплер topK 1/topP 1/temp 0/seed 0, thinking off, automaticToolCalling off, constrainedDecoding off.
- Фраза 1 `voice-20261122-015807-197.wav` 4,6 с: inferenceMs 14 071 (нажатие во время загрузки, waitMs 6 539), ответ add_task {heard «Завтра в 12:00 маникюр», date 2026-11-23, time 12:00, text «Маникюр»}.
- Фраза 2 `voice-20261122-015851-233.wav` 4,8 с: inferenceMs 12 299, conversationMs 7, ответ add_task {heard «двадцать первого декабря в девятнадцать ноль ноль корпоратив», date 2026-12-21, time 19:00, text «Корпоратив»}.
- Промпт — с календарём на 15 строк, текст в журнале целиком; userText «Команда пользователя — в аудиозаписи.»

Backend.CPU)?.threadCount`; т.е. `audioBackend = Backend.CPU(threadCount = N)`. ## 4. Из чего состоит запрос (s2_tokens.py, токенизатор модели; s0_silence.py)
- Вход ≈ 1134 токена = преамбула 999 (системный промпт 828, из них **календарь на 15 дней 238**; объявление инструмента в шаблоне ≈ 171) + ход пользователя ≈ 18 (шаблон + userText 9) + **звук ≈ 115** (4,6 с × 25 ток/с).
- Выход 59–61 токен: `<|tool_call>call:add_task{date:<|"|>2026-11-23<|"|>,heard:<|"|>Завтра в 12:00 маникюр<|"|>,text:…,time:…}<tool_call|>`. Значение `heard` — 12 токенов (фраза 1), обвязка поля ≈ 5 → `heard` ≈ 17 токенов из 59 (≈ 29 % выхода; во фразе 2 значение длиннее).
- Попутная находка (не про скорость): шаблон Gemma 4 сортирует свойства инструмента по алфавиту — в объявлении модель видит `date, heard, text, time`, а не `heard` первым, как задумано в `mechanic_voice.md` («`heard` — первым: модель сначала выписывает услышанное»). И в ответах телефона аргументы идут `date, heard, …` — модель выводит дату ДО `heard`. Задумка «сначала услышанное, потом дата» не работает.
- **Тишина в записях владельца** (окна 20 мс, порог max(4×шум, 5 % пика)): фраза 1 — 1,00 с в начале, 0,24 с в конце (речь 3,36 с из 4,60); фраза 2 — 0,92 с в начале, 0,16 с в конце (речь 3,72 из 4,80). Начальная секунда — реакция после вибрации. Обрезка с запасом 150 мс: 4,60→3,66 с и 4,80→4,02 с, −23 и −20 токенов звука (−17–20 % звука); с запасом 50 мс: −28 и −24 токена. Шум записи очень низкий (RMS 5–7 из 32767) — у телефона шумоподавление, порог по энергии работает уверенно.

## 6. Штатная статистика на телефоне — чем делать разбивку (для агента реализации, по исходникам v0.19.1)
- Kotlin: `ExperimentalFlags.enableBenchmark = true` до создания `Engine` (`ExperimentalFlags.kt:34`), затем после `sendMessage` — `conversation.getBenchmarkInfo()` (`Conversation.kt:682`; без флага бросает `LiteRtLmJniException`).
- Поля `BenchmarkInfo` (`Benchmark.kt:51–60`): `initTimeInSecond`, `timeToFirstTokenInSecond`, `lastPrefillTokenCount`, `lastPrefillTokensPerSecond`, `lastDecodeTokenCount`, `lastDecodeTokensPerSecond`, **`markDurationsInSecond`** — в нём ключ **`"audio_executor"` — время кодирования звука аудиоэнкодером в prefill** (KDoc `Benchmark.kt:30–48`), а также `executor_decode_and_sample` и др. Это прямая разбивка «энкодер / prefill / decode», которой нет в журнале. В Python-обёртке хоста `markDurations` не выведены (в C API 0.19.1 нет функции чтения меток) — на хосте энкодер отделяется косвенно (вариант bare_audio).
- Важно: в «последнем prefill» по замерам хоста число токенов включает звук (1134 = текст + 115 звука), а время — включает работу энкодера (TTFT ≈ время prefill).

- Релизы LiteRT-LM (GitHub API releases): v0.11.0 — MTP Gemma 4 «>2x faster decode on mobile GPUs»; v0.19.0 — «Accelerated Logit Masking… full support for MTP-enabled decoding»; v0.19.1 — аудио Gemma 4 на **Artisan GPU** (бэкенд Google Tensor, только Pixel); v0.14.0 — «NPU and GPU audio acceleration».

Находки:
- **Аудиоэнкодер на CPU хоста ≈ 0,2 с** на 4–5 с звука: это разница «до decode» − «prefill» у вариантов со звуком (0,19–0,22 с), у чистого текста она 0. Штатное «prefill, с» (токены/ток/с из BenchmarkInfo) энкодер **не включает** — он виден только как разрыв между TTFT/«до decode» и prefill. (Уточнение к п. 3: TTFT ≈ prefill там совпал, потому что TTFT ≈ prefill + 0,06 с; здесь разрыв 0,2 с.)
- **Prefill на CPU идёт кусками по 128 токенов** (s5_encoder.py, клипы 1–18,4 с и текст той же длины): 45, 70, 95 токенов — 0,23 с; 135 и 250 — 0,46 с; 480 — 0,93 с; звук и текст той же длины одинаковы. Поэтому обрезка тишины на CPU даёт выигрыш, только если число токенов перешагивает границу 128 (bare_audio 135 → 112 токенов: 0,69 → 0,25 с; в полном запросе 1134 → 1111 — 9 кусков в обоих случаях, выигрыша нет, разница в таблице — шум). На GPU телефона размер куска иной (не измерено).
- **Переиспользование префикса — главный рычаг prefill**: на нажатие остаётся ≈ 212 токенов вместо 1134 (−81 %), prefill 2,5–3,0 → 0,47 с, всего −36…−44 % на CPU хоста. `clone()` разговора — 0–4 мс. Ответы в варианте prefix верные на обеих фразах (date, time, text как у телефона; `heard` иной: «завтра в двенадцать ноль ноль маникюр», «21 декабря в 19:00 корпоратив» — в эмуляции в истории есть предыдущий ход; при настоящем `prefillPrefaceOnInit` + `clone()` истории нет и ответы будут как у варианта split).
- **Decode — половина времени и на хосте: 59–61 токен по 15–19 ток/с = 3,1–4,0 с** — его не уменьшают ни промпт, ни префикс; уменьшают только MTP и длина ответа.

- **prefix + MTP: 5,9 → 2,0 с на CPU хоста (−66 %)**.

## 10. Размер KV-кэша (maxNumTokens) — неожиданно сильный рычаг (CPU хоста)
Модель компилируется под размер кэша (лог: «magic_number=32003, target_number=4096» — сигнатуры prefill/decode и драфтер перестраиваются под `maxNumTokens`), внимание считается по всему выделенному кэшу. Приложение задаёт `maxNumTokens = 4096`.
| maxNumTokens | MTP | full ф1/ф2: prefill с; decode ток/с; всего с | prefix ф1/ф2: всего с |
|---|---|---|---|
| 4096 | OFF | 2,53/2,51; 18,8/18,5; 5,83/5,98 | 3,77/3,72 |
| 4096 | ON | 2,53/2,52; 45,9/29,8; 3,99/4,72 | 1,99/2,08 |
| 1536 | OFF | 1,89/1,85; 26,7/26,9; 4,28/4,35 | 2,61/2,55 |
| 1536 | ON | 1,89/1,82; 64,7/41,5; 2,95/3,46 | **1,44/1,56** |
- 4096 → 1536: prefill −25 %, decode ×1,43 без MTP; с MTP — ×1,4 сверху. Ответы — все верные (проверка date/time/text по каждому запуску).
- Ограничение: кэш должен вместить преамбулу (≈ 1000 токенов сейчас, ≈ 880 без календаря) + звук (25 ток/с; 30 с записи = 750 токенов) + ответ (до 128). При записи до 30 с нужно ≈ 1900 → 2048; при 1536 — запись до ≈ 15 с (без календаря) или до ≈ 10 с (с календарём). Переполнение — ошибка запроса, а не тихая порча (не проверено на телефоне).
- Дополнение: `maxNumTokens = 2048` — почти как 1536: MTP OFF full 1,98/2,01 с prefill, decode 26,4/26,2 ток/с, всего 4,39/4,51 с; MTP ON full 3,17/3,67 с, **prefix 1,50/1,57 с**. Все ответы верные (`out_s4_specON_mnt2048.jsonl`, `out_s4_specOFF_mnt2048.jsonl`). `maxNumTokens = 1280` — **ошибка уже на первом запросе** («Failed to invoke the compiled model / Failed to allocate tensors», `llm_litert_compiled_model_executor.cc:933`), хотя запрос (1134 + 1) в него помещается — малые размеры кэша не годятся; 2048 — безопасный выбор (вмещает и 30 с звука).

## 11. Аудиоэнкодер: окно и потоки (s6_audio_threads.py, `scripts/out_s6.jsonl`; энкодер = sendMs − prefill − decode, медиана из 5)
| потоки звука | клип 1 с | 4,6 с | 9,2 с | 18,4 с |
|---|---|---|---|---|
| 1 | 0,62 | 0,62 | 1,26 | 2,37 |
| 2 | 0,33 | 0,33 | 0,65 | 1,26 |
| 4 (по умолчанию) | 0,25 | 0,33 | 0,38 | 0,56 |
| 8 | 0,12 | 0,13 | 0,26 | 0,36 |
- **Энкодер статический с окном фиксированной длины**: клипы 1; 4,6; 4,8; 5,0; 5,2; 5,6; 6,4; 7,5 с при 1 потоке — одинаково 0,63–0,70 с, 9,2 с — вдвое дольше. Окно ≥ 7,5 с и < 9,2 с (вероятно, 8 с; точно не установлено). Короткая запись дополняется до окна — **обрезка тишины время энкодера не уменьшает** (фразы владельца 4,6–4,8 с — одно окно и до, и после обрезки).
- Потоки масштабируют энкодер почти линейно (1 → 8: 0,62 → 0,12 с на окно). На хосте энкодер — 4–5 % времени запроса; на телефоне его доля неизвестна (журнал не разделяет), см. п. 6 — `markDurationsInSecond["audio_executor"]`.

## 12. Перенос на телефон: что известно и чего нет
- Хост (CPU, 4 потока, кэш 4096, MTP выкл.) — 5,8–6,0 с на запрос: prefill ≈ 2,5 с (43 %), энкодер ≈ 0,25 с (4 %), decode ≈ 3,1–3,3 с (53 %). Телефон на GPU — 12,3–14,1 с, т.е. **вдвое медленнее CPU хоста**, хотя по опубликованным цифрам GPU даже среднего телефона (Mali-G710: prefill 875, decode 19 ток/с) дал бы ≈ 1,3 с prefill + ≈ 3,1 с decode + энкодер на CPU телефона (оценка 0,5–1 с на окно, 4 потока) ≈ 5–5,5 с. **≈ 7 с на телефоне не объясняются опубликованными скоростями** — какая стадия «раздута», без разбивки (п. 6) не определить. Гипотезы для проверки журналом: (а) decode на GPU телефона много медленнее 19 ток/с (кэш 4096 вместо 2048 из условий Google усиливает это — см. п. 10); (б) prefill на GPU медленный на этом SoC; (в) энкодер на CPU телефона медленный (1 окно ≈ 8 с звука при 4 потоках); (г) накладные расходы нового разговора на GPU.
- Что переносится уверенно: **число токенов** (1134 вход, 59–61 выход, звук 25 ток/с, преамбула 999) — одинаково на любом устройстве; **качество ответов** — ответы хоста совпали с телефоном дословно, значит проверки вариантов на хосте действительны для телефона; **относительный эффект MTP** — по Google на мобильных GPU ×1,3–2,2 (карточка, S26 Ultra), на нашем ответе-вызове на CPU хоста ×1,65–2,5; **доля prefill, которую убирает префикс** — −81 % токенов.
- Что не переносится: абсолютные секунды; эффект `maxNumTokens` на GPU (на CPU хоста ×1,4 decode — на GPU не проверено, но механизм — перекомпиляция под размер кэша — общий); стоимость `clone()` на GPU (на CPU 0–4 мс; на GPU копируется KV-кэш в памяти GPU — не измерено).

## 13. Вывод: меры по убыванию ожидаемого выигрыша на телефоне
1. **MTP: `EngineConfig(speculativeDecodingConfig = SpeculativeDecodingConfig(SpeculativeDecodingMode.ON))`** (Kotlin 0.19.1, `Config.kt`). Выигрыш: decode ×1,3–2,2 на мобильном GPU (Google), ×1,65–2,5 на нашем вызове (хост). Если decode на телефоне ≈ половина времени (как на хосте) — **−25…−40 % всего**. Цена: одна строка; файл модели не меняется (драфтер 44 МБ уже внутри); загрузка движка чуть дольше. Риск качества: нет — ответы идентичны в 24 запусках (ON/ADAPTIVE); технический риск — отказ инициализации драфтера на GPU какого-то устройства → нужен откат «без MTP» в уже имеющейся цепочке отката. Рекомендация Google для GPU — ON всегда.
2. **`maxNumTokens` 4096 → 2048.** Выигрыш на CPU хоста: prefill −22 %, decode ×1,4 (всего −25 %), вместе с MTP — ещё ×1,4 к decode. На GPU не проверено (вероятен тот же знак: модель перекомпилируется под размер кэша; опубликованные цифры Google сняты на контексте 2048). Цена: одно число. Риск: 2048 вмещает преамбулу ≈ 1000 + 30 с звука (750) + ответ 128; 1280 не работает вовсе («Failed to allocate tensors»), 1536 работает, но не вмещает 30 с звука с текущим промптом. Качество не меняется (проверено).
3. **Префикс один раз + `clone()` на нажатие** (`ConversationConfig(prefillPrefaceOnInit = true)`, постоянный системный промпт без даты и времени, дата/время/«завтра»/«послезавтра» — текстом в сообщении пользователя перед звуком; вариант split). Выигрыш: prefill на нажатие 1134 → ≈ 180–215 токенов (−81 %); на CPU хоста −36…−44 % всего, с MTP и кэшем 2048 — 5,9 → **1,5 с (−75 %)**. На GPU телефона выигрыш зависит от того, сколько там занимает prefill (по Google на флагмане 1134 токена ≈ 0,3 с — тогда мало; если prefill на этом SoC медленный — много). Цена: средняя — перестройка промпта (тесты `buildSystemPrompt`), хранение «заготовленного» разговора в плагине, пересоздание при смене модели/промпта; память ×2 KV-кэша на время нажатия. Риск качества: вариант split верен на обеих фразах, но проверен только на двух; календарь при этом убирается (при простом удалении календаря фраза 2 дала «Корпоративный»). Почему сейчас не сделано (`mechanic_voice.md`: «время с точностью до минуты в промпте») — снимается переносом времени в сообщение пользователя.
4. **Потоки аудиоэнкодера** `audioBackend = Backend.CPU(threadCount = N)` (по умолчанию 4). На хосте 4 → 8 потоков: 0,25–0,33 → 0,12 с на окно. На телефоне имеет смысл N = число больших ядер (обычно 4–6 у 8-ядерных SoC; больше — упрётся в малые ядра). Выигрыш — доли секунды, если энкодер на телефоне не окажется узким местом (покажет `audio_executor`). Цена: одна строка. Риск: нет.
5. **Опыт: текст на CPU телефона вместо GPU (A/B).** CPU хоста отвечает за 5,9 с против 12,3–14,1 с GPU телефона; у флагманов Google decode CPU ≈ GPU (47 против 52 ток/с). Если GPU телефона слабый, CPU с MTP может оказаться быстрее. Цена: переключатель для замера. Риск: CPU-память ≈ 1,7 ГБ вместо ≈ 0,7 ГБ.
6. **Не рекомендуется:**
   - убрать `heard` (−17 токенов выхода, −29 % decode) — на фразе 2 текст задачи превращается в «Коропоратiv» во всех вариантах без `heard`;
   - минимальный промпт (395 токенов) — неверная дата на фразе 2;
   - обрезка тишины (≈ 1 с в начале каждой записи владельца) — энкодер работает окнами ≥ 7,5 с, время не меняется; экономия 20–23 токенов prefill на GPU незаметна; на CPU помогает только при переходе через границу куска 128 токенов;
   - уменьшение `maxOutputTokens` ниже 128 — ответ и так 59–61 токен, генерация останавливается сама; лимит влияет только на обрезку длинного ответа.
7. **Первым делом — разбивка на телефоне** (п. 6): `ExperimentalFlags.enableBenchmark = true` и `getBenchmarkInfo()` после ответа (`timeToFirstTokenInSecond`, `lastPrefillTokenCount/TokensPerSecond`, `lastDecodeTokenCount/TokensPerSecond`, `markDurationsInSecond["audio_executor"]`). Это бесплатно и сразу покажет, какая из гипотез п. 12 верна; меры 1–2 стоит включать сразу, они дешёвые и без риска качества, мера 3 — после разбивки.
