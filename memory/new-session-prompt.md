## Состояние проекта
Работающее PWA «Секретарь» на `https://greatermagistr007.github.io/secretar_v2/`, репозиторий
`GreaterMagistr007/secretar_v2` (публичный, `master`, Pages собираются из GitHub Actions на каждый
пуш).

Сделано: оболочка PWA · галерея 30 макетов календаря · 40 дизайн-токенов, 30 тем, экран выбора темы,
веб-шрифты с кириллицей · нижняя навигация · сущность «Задача» (создание, список дня, просмотр) ·
**повторения (требование Т-4) и отметки выполнения по конкретному повторению (Т-5)**.

**208 тестов в семи файлах, покрытие измеряемых модулей 100 %**, `svelte-check` и сборка чисты.
К базам тесты не обращаются. Стенд работает в зоне `America/New_York` — не в UTC: проект держится на
плавающих датах из локальных полей `Date`, а в UTC подмена локальных полей на UTC тестами не ловится
вовсе. Менять зону нельзя, не проверив мутацией, что тесты по-прежнему ловят такую подмену.

Не сделано: экран поиска (Т-6), правка и удаление задачи (вопрос В-14), Android через Capacitor
(решение Р-20), серверная часть (Р-22, Р-23).

## Как запускать и проверять
- Локально: `docker run -d --name secretar-dev -p 5173:5173 -v "$PWD":/app -w /app --user "$(id -u):$(id -g)" -e npm_config_cache=/tmp/.npm node:22-alpine npm run dev`
  → `http://localhost:5173/secretar_v2/`; с телефона в той же сети — по адресу машины.
- Проверки: `npm run test`, `npm run check`, `npm run build` — в контейнере `node:22-alpine`,
  таймаут от 400000 мс.
- **Прогон считается зелёным по коду возврата, а не по строке с числом тестов** — правило появилось
  из реального случая: набор был красным из-за пустого `*.test.ts`, а все тесты при этом зелёные.
- Владелец просил **сначала показывать локально**, публиковать после проверки: на Pages мешают
  ожидание сборки и кэш service worker.
- Браузерная проверка: если расширение Claude in Chrome не подключено, работает обход через
  `playwright-core` из кэша npx и Chromium из `~/.cache/ms-playwright` — подробности и приёмы
  (подмена часов, поломка IndexedDB, имитация базы прежней версии) в `memory/feedback_tooling.md`.

## Правила, действующие постоянно
- Роль Claude: документация, создание агентов, постановка задач, проверка их результатов (решение
  Р-6). Реализацию делают агенты; результат агента проверяется самостоятельно, а не принимается на
  веру.
- Каждое действие сразу фиксируется в документации (Р-7). По завершении этапа коммит и пуш —
  обязательны, без запроса (Р-8). Правка файлов проекта — без запроса (Р-9).
- Документация и память только в каталоге проекта; глобальная память Claude не используется (Р-10).
- Вопросы владельцу — только вариантами с плюсами, минусами и рекомендацией; номер с расшифровкой.
- MVP минимальный, берём только то, что можно сделать здесь и сейчас (Р-3).
- Отчёты агентов — в `memory/`, имя не начинается с `report`, запись дописыванием через Bash.
  Проверять агента не реже раза в 3 минуты. **Замолчавший агент — чаще не смерть, а долгое чтение:**
  в прошлой сессии это случилось трижды, и каждый раз агент отвечал на прямой вопрос о живости и
  доводил работу до конца; частичный результат при этом сохраняется отдельным файлом.
- Claude никогда не деплоит: работа доводится до коммита и пуша.

## Уроки прошлой сессии, записанные в правила
Все три — в `docs/rules_work.md`, каждый с причиной из факта:
- прогон зелёный по коду возврата, а не по строке вывода;
- число в документации относится к моменту — вписывать нынешнее значение в запись о прошлом нельзя;
- перед коммитом проходить поиском все сводные места, где предмет правки упомянут.
Главное наблюдение двенадцати раундов ревью: **ложь в документации ни разу не оказалась там, где
правили в прошлый раз** — она всплывала в соседнем абзаце того же файла или в старшем документе,
где то же самое сказано ещё раз.
