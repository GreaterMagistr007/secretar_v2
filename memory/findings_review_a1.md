## Н-3. `nextDay` не дополняет ГОД: на годах меньше 1000 `occurrencesInRange` возвращает мусор
**Важность:** важная (латентный: сегодняшний UI такой вход не порождает — см. ниже)
**Где:** `src/lib/tasks/recurrence.ts:36-47`
**Что не так.** `pad` применяется к месяцу и дню, а год подставляется как есть:
`` `${year}-${pad(month)}-${pad(day + 1)}` ``. Для года меньше 1000 получается строка
с 1-3 цифрами года, и следующий же `parts` её не разбирает: `slice(0, 4)` от `'26-01-02'`
даёт `'26-0'`, `Number('26-0') === NaN`. Дальше перебор идёт по NaN и в результат
попадают несуществующие строки.
**Доказательство.** Цитата:
```
36:  if (day < daysInMonth(year, month)) {
37:    return `${year}-${pad(month)}-${pad(day + 1)}`;
38:  }
...
41:    return `${year}-${pad(month + 1)}-01`;
44:  return `${year + 1}-01-01`;
```
Фактический прогон собранного модуля:
```
occurrencesInRange('0026-01-01','weekly','0026-01-01','0026-01-31')
  → [ '0026-01-01' ]                       // ожидалось 01, 08, 15, 22, 29
occurrencesInRange('0001-01-01','daily','0001-01-01','0001-01-05')
  → [ '0001-01-01', '1-01-02', 'NaN-02-01', 'NaN-01-01', 'NaN-01-01' ]
```
То есть функция отдаёт наружу строки `'NaN-01-01'` как дни вхождения.
**Про достижимость честно.** Шапка модуля сама объявляет такой вход допустимым:
«шаблон даты проекта (\d{4}) пропускает „0026-03-01“», и `DATE_PATTERN`
(`validate.ts:40`) его принимает. Но сетку календаря собирает `toIsoDate`
(`src/lib/date.ts:36`), который год тоже **не** дополняет
(`` `${date.getFullYear()}-${pad(...)}` ``), поэтому для 999 года `from` получается
`'999-12-27'`, `dayNumber` даёт NaN и цикл просто не выполняется — пустые метки вместо
мусора. Год в листалке при этом ничем не ограничен (`CalendarScreen.svelte:268`:
`pickerYear += delta;`), так что до таких лет пользователь докрутить может.
**Что сделать.** Годы дополнять до четырёх знаков: `String(year).padStart(4, '0')`
в обеих ветках `nextDay` (и заодно в `toIsoDate`, иначе несогласованность останется).
`dayNumber` править не нужно — он такие годы обрабатывает верно.

## Проверка пункта C (две реализации хранилища) — расхождений в значениях не нашёл
Сверил ветку за веткой.
- День, нерегулярные. Dexie: `where('date').equals(date).filter(recurrence === 'none')`
  (`dexie-repository.ts:112-116`). Память: `occursOn(task.date, 'none', date)` → `date === start`
  (`recurrence.ts:83-84`). Условие одно и то же.
- День, регулярные. Dexie: `where('recurrence').anyOf(RECURRING).filter(task.date <= date && occursOn(...))`
  (`:117-120`). Условие `task.date <= date` избыточно (его уже делает `occursOn`), но не меняет ответ.
- Диапазон, нерегулярные. Dexie берёт `between(from, to, true, true)` и ставит вхождение на
  `task.date` (`:137-141`, `:152-156`); память получает то же из `occurrencesInRange(start,'none',from,to)`.
- Диапазон, регулярные. Dexie: все задачи с `task.date <= to`, затем тот же `occurrencesInRange`
  (`:142-146`, `:158-162`). Память вызывает его же. Перевёрнутый диапазон: у Dexie
  `between` с lower > upper даёт пустую коллекцию, а `occurrencesInRange` при `from > to`
  возвращает `[]` (`recurrence.ts:110-112`) — обе ветки пустые, как в памяти.
- Отметки. Ключ в обеих реализациях `` `${taskId}|${occurrenceDate}` ``
  (`memory-repository.ts:33-35`, `dexie-repository.ts:102-106`), сопоставление одинаковое.
- Порядок. Обе гонят результат через `sortOccurrences` (`sort.ts:37-45`), ключ сортировки —
  дата, приоритет, id; id уникальны, значит порядок полный и совпадает.
- `RECURRING` и `anyOf`. Dexie копирует переданный массив перед сортировкой
  (`node_modules/dexie/dist/dexie.js:311`: `return arrayLike.slice();`), так что
  `RECURRING as Recurrence[]` (снятие `readonly`) на модульную константу не влияет.
- Миграция. Версия 1 писала `recurrence: 'none'` всем задачам
  (`git show 802522e:src/lib/tasks/dexie-repository.ts`, `recurrence: 'none',`), поэтому новый
  индекс `recurrence` покрывает и старые записи, и ни одна задача прежней базы не выпадает из
  обеих ветек выборки. Отсутствие `upgrade` обосновано верно.
- Задача со значением `recurrence` вне перечня (порча данных) исчезает из выборки в обеих
  реализациях одинаково: Dexie — не попадает ни в одну ветку, память — `occursOn` уходит
  в конец `switch` без `default` и возвращает `undefined`.
Единственные фактические различия — не в значениях:
1. Dexie отдаёт ОДИН И ТОТ ЖЕ объект `task` во всех вхождениях одной задачи
   (`:158-161`: `occurrences.push({ task, date, ... })` внутри цикла), память копирует на каждое
   вхождение (`memory-repository.ts:38-44`). Правка `occurrence.task` в UI у Dexie задела бы
   соседние вхождения, у фейка — нет. Сейчас UI ничего не правит.
2. Выборки Dexie идут тремя отдельными `await` вне транзакции (`:112-124`, `:137-150`):
   между чтением задач и чтением отметок другая вкладка может записать отметку, и на экран
   попадёт рассогласованный снимок. Для одной вкладки безобидно.

## Итог
Находок: критических — 0, важных — 3 (Н-1, Н-2, Н-3), замечаний — 7 (Н-4 … Н-10).

Логика повторений верна: `occursOn` и `occurrencesInRange` сошлись с независимым
генератором на 240 стартах и всех днях четырёхлетнего окна без единого расхождения,
перенос на последний день месяца через `min(startDay, daysInMonth)` работает и в
високосных годах, от часового пояса модуль не зависит, на мусорном входе не зацикливается.
Две реализации хранилища на одних данных дают одинаковые значения — я прошёл по каждой
ветке выборки и различий в ответах не нашёл; миграция схемы обоснована верно, потому что
версия 1 уже писала поле `recurrence`. Ломающих дефектов в слое данных нет.
Всё найденное важное сидит в двух местах. Первое — экран: сообщение об ошибке отметки
не гасится ничем, кроме следующего нажатия флажка, и продолжает висеть под списком
другого дня (Н-1); каждое нажатие флажка поднимает `dayLoading` и полностью
пересоздаёт список, из-за чего теряется фокус и переключение с клавиатуры после первого
же нажатия ломается (Н-2). Второе — `nextDay` не дополняет год до четырёх знаков, и на
годах меньше 1000 `occurrencesInRange` отдаёт наружу строки вида `NaN-01-01` (Н-3);
сегодняшний UI такой вход не порождает только потому, что `toIsoDate` год тоже не
дополняет, то есть держится на второй такой же недоделке.
