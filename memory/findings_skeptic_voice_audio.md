## Находки

### С-1 (блокер для формулировки плана) — `ToolChoice.Required` в выпущенной LiteRT-LM 0.19.1 НЕТ
- Утверждение исследователя (разд. 3.1, 8.1, 8.2): «нативно: ToolSet + `ToolChoice.Required` (constrained decoding)» в LiteRT-LM 0.19.1.
- Проверка:
  - AAR `litertlm-android-0.19.1.aar` (dl.google.com, 21 200 360 байт), `unzip -l classes.jar | grep -i toolchoice` — пусто; при этом `Content$AudioBytes`, `Content$AudioFile`, `OpenApiTool`, `ToolSet` есть.
  - `kotlin/java/com/google/ai/edge/litertlm/Conversation.kt` по тегу v0.19.1: параметра `toolChoice` нет (grep пуст). В ветке main — есть (`Conversation.kt:128 toolChoice: ToolChoice? = null`).
  - История файла (GitHub API commits?path=...Conversation.kt): `904871418f 2026-11-05 Add tool_choice to the Kotlin API.` — коммит в main, в тег v0.19.1 не попал; main впереди v0.19.1 на 376 коммитов (compare API).
- Вывод: `ToolChoice.Required` — только в невыпущенном коде; в Maven его нет. Использовать — значит собирать LiteRT-LM из исходников (Bazel) или ждать 0.20.
- Что есть в 0.19.1 и закрывает ту же цель: `ResponseFormat.json(schema)` (constrained decoding через LLGuidance, `ConversationConfig.enableResponseFormat = true`, `ResponseFormat.kt:39`, коммит 587d1d6b4d от 2026-07-16). Тонкость: `Conversation.resolveResponseFormat` (Conversation.kt:81-91 v0.19.1) молча ОТБРАСЫВАЕТ responseFormat, если `automaticToolCalling=true` и инструменты заданы. Значит рабочая схема на 0.19.1 — без инструментов вовсе: схема JSON `{text,date,priority,recurrence,heard}` как формат ответа; либо инструменты с `automaticToolCalling=false` + `ExperimentalFlags.enableConversationConstrainedDecoding` (но тогда модель вправе ответить текстом — без гарантии вызова).
- Предложение: в плане шага Б заменить «ToolChoice.Required» на «ответ по JSON-схеме (`ResponseFormat.json`)»; результат для JS тот же — объект аргументов `add_task`. Владельцу это не меняет смысла Р-34 («модель вызывает add_task» = модель отдаёт аргументы add_task), но формулировку в docs поправить. Проверить на эмуляторе, что LLGuidance-схема работает вместе с аудиоконтентом (нигде не описано — см. С-3).

### С-2 (важно) — «GPU-вариант 2 340 870 772 байт» — это модель для Web, не для Android
- Утверждение (разд. 2.1, 8.1, 8.3): `gemma-4-E2B-it-gpu.litertlm` 2,34 ГБ — GPU-файл для телефона, «самый маленький».
- Проверка: карточка `litert-community/gemma-4-E2B-it-litert-lm` (README, скачан 2026-11-21): «Web on LiteRT-LM uses a specially optimized model (ссылка на gemma-4-E2B-it-gpu.litertlm) for Web because of its unique memory constraints» и «See our LiteRT-LM.js overview ... using the gemma-4-E2B-it-gpu.litertlm model file». Таблица Android: и CPU, и GPU на S26 Ultra — «Model size 2583 MB», т.е. один и тот же основной файл `gemma-4-E2B-it.litertlm`.
- Вывод: для Android (и CPU, и GPU) — один файл 2 588 147 712 байт. Работа `-gpu`-файла на Android не документирована. Цифру 2,34 ГБ из расчётов для APK убрать.

### С-3 (важно) — «аудио Gemma 4 на GPU появилось только в 0.19.1» — неверное прочтение; «Artisan» = бэкенд Google Tensor
- Утверждение (разд. 2.1, 3.3): релиз v0.19.1 «vision and audio support for Gemma 4 on the Artisan GPU backend» → «на GPU-бэкенде аудио для Gemma 4 появилось только в последней версии».
- Проверка: `Config.kt` v0.19.1: `class GOOGLE_TENSOR : Backend("GOOGLE_TENSOR_ARTISAN")` — Artisan это отдельный бэкенд под чипы Google Tensor (Pixel), не общий GPU. Ещё v0.14.0 (2026-07-08): «NPU and GPU audio acceleration». v0.8.0 (2025-11-25): «Vision and Audio input are supported when models support it», Kotlin API.
- Но: официальный пример (`docs/api/kotlin/getting_started.md`, v0.19.1, раздел 5) ставит `audioBackend = Backend.CPU() // Or Backend.NPU(...)` — GPU для аудиоэнкодера в примере не назван. Значит надёжная конфигурация: `backend = GPU` (текстовый декодер), `audioBackend = CPU`. Работает ли `audioBackend = GPU` на обычном Adreno/Mali — не установлено, проверять опытом; первым ставить CPU.
- Вывод: требовать именно 0.19.1 из-за аудио не нужно; 0.19.1 брать просто как последнюю. Утверждение исследователя в отчёте поправить.

### Уточнение к С-3 (после разбора заголовков) — «Artisan» шире, чем Google Tensor
- Разобрал заголовки (flatbuffers, Range-запрос первых 256 КБ, свой парсер по `schema/core/litertlm_header_schema.fbs` v0.19.1) трёх файлов. В `gemma-4-E2B-it-gpu.litertlm` и `-web.litertlm` текстовый декодер — секция `tf_lite_artisan_text_decoder` с `backend_constraint = gpu_artisan`. Значит «Artisan» — особый формат GPU-декодера (его используют Web-файлы и бэкенд `GOOGLE_TENSOR_ARTISAN`), а не только Pixel. Запись v0.19.1 «audio on Artisan GPU» касается именно `-gpu`/`-web`-файлов, а не основного файла.
- Основной файл `gemma-4-E2B-it.litertlm` — декодер `tf_lite_prefill_decode` (обычный LiteRT GPU/CPU), аудио с ним работает с v0.8.0. Вывод С-3 в части «требование 0.19.1 для звука не обосновано» остаётся.

### С-4 (важно) — в основном файле аудиоэнкодер жёстко привязан к CPU
- Разбор секций `gemma-4-E2B-it.litertlm` (байт): LlmMetadata 12 192; SP_Tokenizer 4 689 013; `tf_lite_embedder` 103 811 720; `tf_lite_per_layer_embedder` 1 284 518 392; `tf_lite_audio_encoder_hw` 94 052 280 (backend_constraint=cpu); `tf_lite_audio_adapter` 9 441 244 (cpu); `tf_lite_end_of_audio` 6 772; `tf_lite_vision_encoder` 224 137 936; `tf_lite_vision_adapter` 4 742 928 (cpu); `tf_lite_end_of_vision` 6 772; `tf_lite_prefill_decode` 818 275 184; `tf_lite_mtp_drafter` 44 325 712. Сумма 2 588 020 145 (+заголовок = 2 588 147 712, совпадает с HF).
- Вывод: аудиоэнкодер (94 МБ) идёт только на CPU (`audioBackend = Backend.CPU()`), на GPU — только текстовая часть. Время энкодера на CPU войдёт в каждое нажатие на любом телефоне. Это же совпадает с примером `getting_started.md` v0.19.1 (`audioBackend = Backend.CPU() // Or Backend.NPU`).
- Предложение: в плагине — `backend = GPU` (с откатом на CPU при ошибке инициализации), `audioBackend = CPU`; в замерах шага Б отдельно мерить время энкодера.

### С-5 (важно) — модель меньшего размера, влезающая в 2 ГиБ, у Gemma 4 E2B невозможна даже урезанием
- Если вырезать зрение (224 137 936 + 4 742 928 + 6 772 = 228 887 636) и MTP-драфтер (44 325 712) — останется ≈ 2 314 934 364 байт, всё ещё больше 2 ГиБ (2 147 483 648) на ~167 МБ. Урезание `litert_lm_builder` (есть в репозитории, `python/litert_lm_builder/`) задачу «в APK» не решает.
- Файл `-web.litertlm` 2 008 432 640 меньше 2 ГиБ, но это Artisan-декодер для браузера; в его заголовке секций аудиоэнкодера в первых 256 КБ не найдено (только `tf_lite_artisan_text_decoder`), работа на Android не документирована — не кандидат.
- По сути предела APK: утверждение исследователя про `Math.toIntExact(apkSigningBlockOffset)` подтверждаю по исходнику AOSP main (`VerityBuilder.java:314` и `:469`), но срабатывает ли этот путь для нашей подписи (есть ли verity-дайджест) — не проверено ни им, ни мной. Довод решающий и без этого: LiteRT-LM берёт только путь к файлу (`EngineConfig.modelPath: String`, `Config.kt` v0.19.1, конструктор без FileDescriptor), значит модель из APK всё равно придётся скопировать в отдельный файл — 2,6 ГБ в APK + 2,6 ГБ копия. Опыт с заглушкой 2,6 ГБ (п. 8.4 исследователя) делать не нужно: даже успех ничего не даёт, кроме удвоения места.

### С-6 (важно, упрощение) — Kotlin и корутины не нужны: API вызывается из Java как есть
- Проверка по исходникам v0.19.1:
  - `EngineConfig` и `ConversationConfig` — `data class ... @JvmOverloads constructor` (Config.kt:209-220, 275-294).
  - `Engine.initialize()` — обычный блокирующий метод (Engine.kt:61), `createConversation(...)` — обычный.
  - `Conversation.sendMessage(...)` — синхронный, `@JvmOverloads` (Conversation.kt:115-170, «This is a synchronous call»); есть `sendMessageAsync(..., MessageCallback)` с Java-интерфейсом обратного вызова (Conversation.kt:281, 825). `suspend`-функций в Engine/Conversation нет (grep пуст); Flow — только в отдельной перегрузке, её можно не использовать.
  - Инструменты — `OpenApiTool` (интерфейс: `getToolDescriptionJsonString()`, `execute(String)`) реализуется на Java; верхнеуровневая `tool(...)` из Java — через класс файла Tool.kt (имя класса `ToolKt` — по умолчанию Kotlin, не проверено сборкой).
  - `ResponseFormat.json(String)` — `@JvmStatic`.
  - `ExperimentalFlags` требует `@OptIn` только в Kotlin; из Java ограничение не действует.
- Цена: Kotlin Gradle-плагин в `android/` не нужен; придут транзитивные зависимости AAR (POM 0.19.1): gson 2.14.0, kotlin-reflect 2.4.0 (+kotlin-stdlib), kotlinx-coroutines-android 1.11.0 — несколько МБ в APK, `minifyEnabled false` у нас (app/build.gradle). Конфликт версий kotlin-stdlib с Capacitor 8 — не проверено (проверяется первой сборкой `./gradlew :app:dependencies`).
- Предложение: плагин писать на Java рядом с `TaskNotifierPlugin.java` — в стиле проекта, без нового языка. Исследователь пишет «свой Kotlin-плагин» (разд. 3.3, 8.2) — это необязательно.

### С-9 (важно) — загрузка модели: до 10 с, на каждое нажатие нельзя; держать загруженной только пока приложение на экране
- `Engine.initialize()` — документация в коде (Engine.kt:53-60 v0.19.1): «can take a significant amount of time (e.g., 10 seconds)», рекомендуют фоновый поток. `cacheDir` ускоряет второй запуск (Config.kt, getting_started.md).
- Память: карточка — «weight footprint in memory can be as low as 0.8 GB while the runtime uses memory mapping to support the 1.12GB of embedding parameters», «Vision and Audio models are loaded on demand»; S26 Ultra CPU 1733 МБ (ru_maxrss), GPU 676 МБ CPU-памяти + GPU-память (не указана). Аудиоэнкодер (94 МБ, только CPU) добавится при первом звуке.
- Убийство процесса: в фоне приложение с ~2 ГБ RSS — первый кандидат для lowmemorykiller (не измерено; общее свойство Android: фоновые кэшированные процессы убиваются первыми, большие — раньше). На экране — риск мал на 8+ ГБ.
- Предложение для шага Б (и вопрос владельцу В-в): грузить Engine в фоне при открытии приложения (или экрана календаря), закрывать (`engine.close()`) при уходе приложения в фон (`handleOnPause/handleOnStop` плагина Capacitor); на нажатие — только запись и запрос. Системный промпт с датой — через `ConversationConfig(prefillPrefaceOnInit = true)` один раз, на каждое нажатие — `conversation.clone()` (есть в 0.19.1, Conversation.kt:746, коммит a8b2535801 от 2026-10-20): история не копится, промпт не считается заново. При смене даты (полночь) — пересоздать «эталонный» разговор. В замерах шага Б отдельно: холодный `initialize()`, второй `initialize()` с `cacheDir`, `createConversation` с префиллом, `clone()`, запрос.
- Хранить модель в `filesDir`/`getExternalFilesDir`, не в `cacheDir` (система чистит кэш при нехватке места).

### С-10 (замечание) — запись: нативно, согласен; две детали
- Нативная запись `AudioRecord` 16 кГц моно PCM16 → WAV — правильно: WebView `MediaRecorder` даёт webm/opus, его пришлось бы декодировать (`decodeAudioData`), пересэмплировать и упаковывать в WAV в JS; плюс цепочка разрешений `getUserMedia` через WebChromeClient. Нативно — проще и без конвертации.
- Деталь 1: старт `AudioRecord` занимает время (десятки–сотни мс, не измерено); пользователь начинает говорить в момент нажатия → первый слог может пропасть. Предложение: сигнал готовности (короткая вибрация `HapticFeedback` или смена вида кнопки) после фактического старта записи; в замерах — задержка от `pointerdown` до первого буфера.
- Деталь 2: предел модели — 30 с звука (ai.google.dev/gemma/docs/capabilities/audio, подтверждено поиском); запись обрезать на 30 с, при коротком нажатии (< 0,3–0,5 с) не отправлять в модель.
- Деталь 3: `Content.AudioBytes` уходит в нативный слой как base64 внутри JSON (Message.kt:189-195) — для 5 с PCM16 это ~213 КБ строки, некритично; `Content.AudioFile(path)` избегает лишней копии — для записи с микрофона можно писать WAV во временный файл в `cacheDir` и передавать путь.

### С-11 (важно, план) — самый дешёвый первый опыт пропущен: та же модель и тот же рантайм на нашей Linux-машине
- Проверка: PyPI `litert-lm-api` 0.19.2 (13.11.2026) — колёса `manylinux_2_27_x86_64` (33,2 МБ), `manylinux_2_27_aarch64`, `win_amd64`, `macosx_12_0_arm64`, `android_23_x86_64/arm64_v8a`; `litert-lm` 0.19.2 — CLI. Документация Python (developers.google.com/edge/litert-lm/python): `litert_lm.Engine(path, audio_backend=litert_lm.Backend.CPU())`, `Content.AudioFile(absolute_path=...)`, инструменты — обычные функции Python. CLI (developers.google.com/edge/litert-lm/cli/usage): `litert-lm run <model> --attachment=audio.wav --prompt=...`, `--preset=preset.py` для инструментов. (Флаг `--audio-backend=gpu` в примере CLI относится к десктопу; для основного файла аудио всё равно CPU, см. С-4.)
- Вывод: качество русской речи, точность дат и формат ответа можно измерить на хосте (в docker-контейнере, по правилам проекта) на том же файле `gemma-4-E2B-it.litertlm` до единой строки Android-кода. Скорость хоста к телефону не относится, качество — относится (те же веса; численные расхождения x86/ARM малы, не проверено).
- Предложение — порядок экспериментов (замена А/Б/В):
  0. Владелец отвечает на вопросы ниже (телефон, «встроена»).
  1. **Шаг 1 (хост, без Android):** владелец записывает диктофоном телефона 20–30 своих фраз (разные формулировки дат, «в 12», «каждый вторник», приоритет, шум улицы); агент переводит в WAV 16 кГц моно (ffmpeg в контейнере) и гоняет через Python-API: E2B и E4B, промпт с таблицей 14 дней, ответ по JSON-схеме (С-1). Итог — таблица «фраза → heard/date/priority/recurrence, верно/неверно». Здесь же дешёво сравнить двухшаговый путь (GigaAM v3 через sherpa-onnx Python → тот же E2B текстом), чтобы у владельца были цифры, а не догадки (С-14). Стоимость: ~5,2 ГБ скачивания (E2B + E4B) и один скрипт.
  2. **Шаг 2 (телефон владельца, без нашего кода):** Google AI Edge Gallery 1.0.23, задача «Ask audio» на Gemma-4-E2B — время ответа и то, что модель вообще запускается на его телефоне (порог Google 8 ГБ, С-7; Gallery требует Android 12+, `minSdk = 31`). Это бывший шаг А, но цель другая: не качество (оно в шаге 1), а скорость и память на его железе. Если телефон не тянет — шаги 3–4 не начинаются.
  3. **Шаг 3 (плагин на Java, эмулятор):** как шаг Б постановщика, с поправками С-1, С-4, С-6, С-9, С-10; на эмуляторе — WAV-файлом, только цепочка «звук → JSON → задача».
  4. **Шаг 4 (телефон):** микрофон, замеры (холодная загрузка, энкодер, полный цикл).
- Лишнее в плане постановщика: сравнение E2B/E4B на телефоне (шаг В) — качество уже будет из шага 1, а E4B по порогу Google требует 12 ГБ; на телефоне сравнивать только если шаг 1 покажет, что E2B не хватает. Опыт «APK > 2 ГиБ с заглушкой» (п. 8.4 исследователя) — не нужен (С-5).
- Чего не хватает: вопросов о телефоне владельца (С-7), критерия приёмки («сколько из 30 фраз должно быть верно и за сколько секунд» — задать владельцу до опытов, иначе сравнение моделей нечем завершить), настроек декодирования (С-12), проверки доступа к HF из сети владельца (С-8).

### С-12 (важно) — настройки декодирования не заданы в плане, а они влияют и на скорость, и на качество
- Gallery по умолчанию для Gemma-4-E2B: `temperature 1.0`, `topK 64`, `topP 0.95`, `maxTokens 4000`, возможности `llm_thinking`, `speculative_decoding` (model_allowlists/1_0_23.json). Для разбора команды это неподходящие значения: случайность выбора и возможное «размышление» удлиняют и портят ответ.
- В API 0.19.1 есть: `SamplerConfig` (в `ConversationConfig`), `ThinkingConfig(enableThinking=false)` (Config.kt), `maxOutputToken`, `speculativeDecodingConfig` (MTP-драфтер есть в файле, секция `tf_lite_mtp_drafter` 44 МБ).
- Предложение: в шаге 1 зафиксировать — жадный выбор (temperature 0 / topK 1; точные имена полей SamplerConfig — сверить при написании), размышление выключено явно, `maxOutputToken` ≈ 128, MTP включить и сравнить. Гипотеза для проверки там же: поле `heard` ставить ПЕРВЫМ в JSON-схеме — модель сначала выписывает услышанную фразу, затем выводит дату из неё; порядок полей при ограниченном декодировании может влиять на точность (не проверено).

### С-13 (замечание) — пропущенные кандидаты: новых годных не нашёл
- ML Kit GenAI Prompt API (Gemini Nano 4 на базе Gemma 4, AICore): по найденным материалам (developers.google.com/ml-kit/genai; android-developers.googleblog.com/2026/07/android-on-device-inference.html) звук идёт через отдельный GenAI Speech Recognition API, а Prompt API — текст и картинки; «Advanced mode» — Pixel 10 и немногие устройства. Сама карточка Gemma 4 E2B LiteRT называет AICore «recommended path for production» на поддерживаемых устройствах. Для Р-34 не подходит (отдельный шаг распознавания, привязка к устройству), но если у владельца Pixel 10 — стоит знать.
- Samsone (arXiv 2609.21666, Interspeech 2026): аудиомодели 99M/134M/356M (энкодер на базе Whisper-Tiny + SmolLM2), есть мобильные чекпойнты. Основа SmolLM2 — англоязычная; русский и вызов функций не заявлены (по аннотации; полный текст не читал). Не кандидат.
- Аудио-LLM меньше 1–1,5 ГБ с заявленным русским и вызовом функций — не найдено (поиск 2026-11-21, ограниченный). Вывод исследователя «таких нет» не опровергнут; LFM3-Omni-2B (1,3 ГБ GGUF) — без русской речи в списке языков.

### С-14 (важно, для решения владельца) — «встроена в приложение» буквально достижима только двухшаговым путём
- Факты: аудиомодели с вызовом функций и русским — от 2,3 ГБ (Gemma 4 E2B, С-5: даже урезанная > 2 ГиБ). Двухшаговый путь из отчёта исследователя (разд. 6): GigaAM v3 0,16 ГБ + FunctionGemma 0,29 ГБ ≈ 0,45 ГБ или + Qwen3-1.7B Q4 1,1 ГБ ≈ 1,27 ГБ — под 2 ГиБ, т.е. в APK помещается (sherpa-onnx умеет читать модель из assets через AssetManager — по отчёту исследователя, мной не проверено; текстовой LLM всё равно нужна копия в файл).
- Значит у владельца реальная развилка: (а) «звук сразу в модель» — модель отдельным файлом рядом с APK; (б) «модель внутри APK» — только с отдельным шагом распознавания и маленькой текстовой моделью (качество разбора дат у 0,3–1,7B моделей — под вопросом, разд. 1 отчёта: модели до 2B 10–14 баллов BFCL-V4). Оба пожелания Р-34 одновременно не выполнимы. Исследователь сводит это к уточнению формулировки — недостаточно, это выбор с ценой.

### С-15 (замечание) — «модель — сменная часть»: реалистичный объём
- Без нового кода меняются только модели того же рантайма и того же формата ответа: Gemma 4 E2B ↔ E4B (`.litertlm`, LiteRT-LM). Кандидаты на llama.cpp/MNN (LFM3-Omni, Ultravox) — второй рантайм, второй нативный модуль, другой разбор вызова. По правилу минимального изменения общий интерфейс под несколько рантаймов заранее не строить: плагин с одним методом «обработать запись» и путём к файлу в настройках уже даёт сменность в пределах LiteRT-LM; второй рантайм — только если шаг 1 покажет, что Gemma 4 не годится.

- Дополнение к С-12: `SamplerConfig(topK: Int, topP: Double, temperature: Double, seed: Int = 0)` (Config.kt:310 v0.19.1) — жадный выбор: `topK = 1, topP = 1.0, temperature = 0.0`; из Java все четыре аргумента передаются явно (`@JvmOverloads` у этого класса нет). Там же `LoraConfig(loraPath, audioLoraPath)` — в рантайме есть аудио-LoRA; путь «дообучить слух на русских командах» технически существует (на будущее, в бэклог, не в MVP).

## Вопросы владельцу (варианты, плюсы/минусы, рекомендация)

### В-а. Телефон, на котором будет работать голос
Нужно: модель, объём ОЗУ, версия Android, свободное место (Настройки → О телефоне). Это не выбор, а исходные данные: Google ставит для Gemma 4 E2B порог 8 ГБ ОЗУ, для E4B — 12 ГБ (С-7); Gallery для проверки — Android 12+.

### В-б. Что значит «модель встроена в приложение» (уточнение Р-34)
- **Вариант 1 — модель отдельным файлом рядом с приложением; работает внутри приложения без сети.** APK как сейчас (десятки МБ); файл модели 2,6 ГБ один раз копируется на телефон (с компьютера по USB либо скачивается приложением при первом запуске с Hugging Face). Плюсы: звук сразу в модель (буква Р-34), модель меняется без пересборки APK, обновления APK лёгкие. Минусы: один дополнительный шаг при установке; при скачивании — нужна сеть один раз и доступ к Hugging Face (из России не проверено, С-8); 2,6 ГБ места.
- **Вариант 2 — всё внутри одного APK.** Возможен только с отдельным шагом распознавания (GigaAM 0,16 ГБ) и маленькой текстовой моделью (0,3–1,1 ГБ), С-14. Плюсы: одна установка, ничего не докачивать. Минусы: противоречит «звук сразу в модель»; маленькие текстовые модели заметно хуже разбирают фразы (по бенчмаркам), качество на русских датах не измерено; APK 0,5–1,3 ГБ при каждом обновлении.
- **Вариант 3 — Gemma 4 внутри APK.** Невозможен: файл модели 2,59 ГБ, урезанный — 2,31 ГБ, больше предела 2 ГиБ (С-5); да и рантайм всё равно копирует модель в отдельный файл (двойной расход места).
- **Рекомендация: вариант 1.** Единственный, где сохраняется главное в Р-34 — понимание прямо со звука; дополнительный шаг одноразовый. Способ доставки внутри варианта 1 (копирование с компьютера или скачивание в приложении) — для MVP копирование с компьютера и выбор файла (без кода скачивания, решение Р-3); скачивание — в бэклог с триггером «появился второй пользователь».

### В-в. Когда загружать модель в память
- **Вариант 1 — при открытии приложения, в фоне; выгружать при сворачивании.** Плюсы: к первому нажатию модель обычно готова. Минусы: каждое открытие приложения тратит до ~10 с работы процессора и ~1–2 ГБ памяти, даже если голос не нужен; расход батареи.
- **Вариант 2 — при первом нажатии кнопки; держать, пока приложение открыто.** Плюсы: без голоса ничего не тратится. Минусы: первое нажатие после открытия ждёт загрузку (до ~10 с по документации, на его телефоне не измерено).
- **Вариант 3 — держать всегда, в том числе в фоне.** Минусы: система будет убивать процесс с 2 ГБ в фоне; не работает надёжно. Не рекомендую.
- **Рекомендация: решить после замера на его телефоне (шаг 2/4).** Если холодная загрузка ≤ 2–3 с — вариант 2; если дольше — вариант 1.

### В-г. Критерий «модель годится» (нужен до опытов)
- Предложение по умолчанию: из 30 своих фраз верно разобрано ≥ 27 (дата, приоритет, повтор, текст), ответ ≤ 3 с после отпускания кнопки на его телефоне. Плюс: эксперименты заканчиваются решением, а не бесконечным сравнением. Минус: цифры условные — владелец может назвать свои.

### В-д. Если Gemma 4 плохо понимает русскую речь на шаге 1
- **Вариант 1 — двухшаговый путь (GigaAM → Gemma 4 текстом)**: лучший открытый русский распознаватель, текст фразы виден сразу; отступление от «без отдельного шага» Р-34, +0,16 ГБ.
- **Вариант 2 — Gemma 4 E4B**: тот же путь «звук сразу в модель», но 3,7 ГБ и порог 12 ГБ ОЗУ.
- **Вариант 3 — отказаться от офлайна, вернуться к облаку (В-18 прежние варианты).**
- **Рекомендация:** спрашивать только если шаг 1 провален; заранее не решать — цифры шага 1 покажут, какой из вариантов вообще нужен.

## Итог ревью
- Блокер для плана как написан: `ToolChoice.Required` отсутствует в выпущенной LiteRT-LM 0.19.1 (С-1); замена — ответ по JSON-схеме `ResponseFormat.json` (есть в 0.19.1).
- Фактические ошибки отчёта исследователя: `-gpu.litertlm` (2,34 ГБ) — модель для Web, для Android один файл 2,59 ГБ (С-2); «аудио на GPU только с 0.19.1» — неверное прочтение «Artisan» (С-3); аудиоэнкодер основного файла жёстко на CPU (С-4).

- Упрощения: Java вместо Kotlin (С-6); первый опыт — на хосте Python-API на том же файле (С-11).
- Риски: порог Google 8 ГБ ОЗУ при неизвестном телефоне владельца (С-7); загрузка до 10 с (С-9); качество русской речи не измерено нигде (подтверждаю вывод исследователя).
- Вопросы владельцу: В-а (телефон), В-б («встроена» — рекомендация: файл рядом), В-в (когда грузить), В-г (критерий годности), В-д (запасной путь — только после шага 1).
