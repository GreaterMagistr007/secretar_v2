# Грабли инструмента

Только про поведение Claude Code, не про продукт. Продуктовые выводы и решения — в `../docs/`.

## Режим auto mode блокирует запись в `.claude/settings.json` (2026-09-13, подтверждено)
**Симптом:** создание `.claude/settings.json` отклоняется с текстом `Permission for this action was denied by the Claude Code auto mode classifier. Reason: [Self-Modification]`. Отказ приходит без диалога с владельцем — вопрос до него не доходит.
**Что проверено:** отклонены обе попытки — Bash-heredoc и инструмент `Write`. В глобальном `~/.claude/settings.json` в `permissions.allow` уже есть `Bash(*)`, и это от отказа не спасло: классификатор смотрит на характер действия, а не на permission-правило. Подсказка в тексте отказа («добавьте Bash permission rule») этим контрпримером не подтверждается.
**Обход, который сработал:** владелец переключил режим сессии на `accept edits`, после чего файл записался обычным инструментом `Write` без дополнительных запросов.
**Как действовать дальше:** правки `.claude/settings.json` и других настроек Claude Code выполнять из режима `accept edits`. Из auto mode — не пытаться: это не вопрос формулировки команды.

## Хуки кэшируются на момент старта сессии (2026-09-13)
Созданный `.claude/settings.json` в текущей сессии не действует: нужен `/hooks` или перезапуск. Следствие — проверить разрешения «на ходу» невозможно, поэтому хуки проверялись прогоном их команд напрямую через `sh -c` с подстановкой JSON на stdin.

## Смена режима сессии меняет набор запросов подтверждения (2026-09-13, подтверждено)
**Симптом:** после выхода из auto mode в режим `accept edits` подтверждения начали появляться на каждое действие браузерных инструментов Claude in Chrome — переход по ссылке, снятие скриншота.
**Причина:** `acceptEdits` авто-одобряет только правки файлов; все прочие инструменты идут через обычные permission-правила. В глобальном `~/.claude/settings.json` в `permissions.allow` браузерных инструментов нет (там `Read`, `Glob`, `Grep`, `WebSearch`, `WebFetch`, `Agent`, `Bash(*)`, `mcp__gitlab__*`, `mcp__sentry__*`), поэтому каждый вызов `mcp__claude-in-chrome__*` спрашивал.
**Побочный эффект:** снятие скриншота дважды завершилось ошибкой `CDP sendCommand "Page.captureScreenshot" timed out after 30000ms` — таймаут CDP истекал, пока ждали подтверждения.
**Что сделано:** в проектный `.claude/settings.json` добавлены `mcp__claude-in-chrome__*`, `Bash`, `Monitor`, `Agent`, `WebFetch`, `WebSearch` и фоновые задачи — и в `permissions.allow`, и отдельными блоками хуков `PreToolUse` и `PermissionRequest`. Применяется со следующей сессии (хуки кэшируются на старте).
**Чего это не снимает:** собственные диалоги расширения Claude in Chrome в браузере — они настраиваются в самом расширении, разрешением для конкретного сайта.

## Расширение Claude in Chrome может не подключиться — обход без новых зависимостей (2026-09-27)
`mcp__claude-in-chrome__tabs_context_mcp` вернул «Browser extension is not connected»,
`list_connected_browsers` — пустой список. Перезапуск Chrome владельцем в этот момент был
невозможен, а браузерная проверка требовалась: слой Dexie юнит-тестами не покрывается, и ветка
`anyOf` по обычному индексу типами не подтверждается.

**Обход, сработавший без скачиваний и без правки `package.json`:** на машине уже есть
`playwright-core` в кэше npx (`~/.npm/_npx/*/node_modules/playwright-core`) и браузеры Playwright
(`~/.cache/ms-playwright/chromium-1243/chrome-linux64/chrome` — путь именно `chrome-linux64`,
не `chrome-linux`, старый путь даёт «executable doesn't exist»). Скрипт на Node с импортом
`playwright-core/index.mjs` и `chromium.launch({ executablePath, args: ['--no-sandbox'] })`
поднимает настоящий браузер, открывает dev-сервер в контейнере и работает с IndexedDB.

Полезные приёмы из этой проверки:
- имитация базы прежней версии: `indexedDB.deleteDatabase`, затем ручное создание стора с
  индексами версии 1. **Версию брать 10, а не 1:** Dexie нумерует IndexedDB как «версия × 10»,
  поэтому Dexie-версия 1 — это IDB 10, а версия 2 — IDB 20;
- проверка ветки ошибки без правки кода: подмена `IDBObjectStore.prototype.put` на бросающую
  функцию прямо в странице — так проверено, что сообщение об ошибке действительно показывается;
- ложный FAIL в собственном скрипте: сравнение `document.activeElement` со строкой `select` не
  сходится, потому что у `<select>` свойство `type` равно `select-one`. Приложение было верным.

## Агенты делят одну scratchpad-директорию и затирают файлы друг друга (2026-09-27, подтверждено)
**Симптом:** агент, разбиравший макеты v01–v10, замолчал на шесть минут при пустом отчёте; проверка связи
показала, что Bash и Read работали. Причина оказалась другой: второй агент положил в общую
scratchpad-директорию свой скрипт расчёта контраста под тем же именем `wcag.py` и сменил его интерфейс.
Первый агент получил мусорные числа и пересчитывал всё заново под именем `wcag_agent_a.py`.
**Следствие для постановки задач:** параллельным агентам задавать разные имена временных файлов
(суффикс с именем агента) либо требовать держать скрипты в собственном подкаталоге. Общая директория
у них действительно общая, изоляции нет.
**Второе следствие:** «агент молчит» не равно «агент умер» и не равно «инструмент отказал» — у молчания
бывает третья причина: агент переделывает работу, испорченную соседом. Проверка связи стоит дёшево и
отвечает на это точнее, чем догадки по размеру файла.

## Telegram, GitHub и эмулятор: что работает (2026-11-21)
- **`tlg-send` умеет только текст.** APK отправлялся Bot API напрямую: токен и чат читаются из `~/.config/tlg-send/config` (строки `token=`, `chat_default=`) в переменные внутри одной команды, на экран не выводятся; `curl -F chat_id=... -F document=@secretar.apk --form-string caption=... https://api.telegram.org/bot$T/sendDocument` → ждать `http=200`.
- **Скриншот владельца из Telegram:** `tlg-read --peek --json --timeout 0` → `file_id` самой большой `photo` → `getFile?file_id=` → скачать `https://api.telegram.org/file/bot$T/<file_path>` во временный каталог `memory/tmp_*`; после разбора — `tlg-read --timeout 0`, чтобы сдвинуть offset, и удалить каталог.
- **`gh` не установлен.** Статус публикации Pages — публичный API без токена: `curl -s https://api.github.com/repos/GreaterMagistr007/secretar_v2/actions/runs?per_page=1`. Ожидание через цикл с `gh` зациклилось: ошибка «команда не найдена» по-русски не совпала с шаблоном `*rror*`.
- **Эмулятор Android для локальных тестов APK:** docker-образ `secretar-emu-check` (Android 15, `google_apis` x86_64), запуск с `--device /dev/kvm`, headless swiftshader — протокол команд в `findings_android_emulator.md`, точный будильник и Doze — в `findings_exact_alarm.md`. Владелец велел образ не удалять. Часы переводить `cmd alarm set-time` минимум за 2 минуты до события (иначе окно будильника сжимается само и проверка ничего не доказывает), процесс убивать `am kill`, не `force-stop` (тот снимает будильники).
- **Браузерная проверка с подменой часов:** `playwright-core` из кэша npx, `context.timezoneId` + `page.clock.install({ time })` + `page.clock.runFor(ms)` — так проверен переход выбора дня через полночь без ожидания.
- **Предел Bot API на отправку файла — 50 МБ** (`sendDocument` → HTTP 413). APK с LiteRT-LM под две архитектуры — 54,6 МБ; по умолчанию собирается только arm64-v8a (27,8 МБ), для эмулятора — `SECRETAR_ABIS=arm64-v8a,x86_64` (docs/mechanic_android.md, «Сборка APK»).
