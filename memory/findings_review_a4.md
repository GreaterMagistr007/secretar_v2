## З-2. Обоснование отказа от `$state` для `loadedDate` преувеличено: бесконечного цикла не было бы

**Важность:** замечание
**Где:** `src/routes/CalendarScreen.svelte:85-89`
**Что не так.** Комментарий утверждает:
> `* Намеренно обычная переменная, а не $state: её читает только эффект ниже, и будь она`
> `* реактивной, запись в неё перезапускала бы этот же эффект без конца.`

«Без конца» — неверно. Цикл сошёлся бы после одного лишнего чтения.
**Доказательство.** Установлена svelte 5.57.0. Источник `$state` сравнивает значения перед
уведомлением: `internal_set` начинается с `if (!source.equals(value))`
(`node_modules/svelte/src/internal/client/reactivity/sources.js`), а `equals` для значения по
умолчанию — `return value === this.v;`
(`node_modules/svelte/src/internal/client/reactivity/equality.js:4-6`). Последовательность при
реактивном `loadedDate`: прогон для дня A читает `loadedDate` (= B) → чтение → `.then` пишет
`loadedDate = A`, значение изменилось → эффект перезапускается → второй прогон читает `loadedDate`
(= A), очистку пропускает, запускает ВТОРОЕ чтение A → `.then` пишет `loadedDate = A`, значение
прежнее → уведомления нет → остановка. Итог: одно лишнее чтение на каждую смену дня, а не
бесконечный цикл.
**Что сделать.** Решение (обычная переменная) правильное и менять его не надо — лишнее чтение
дня при каждом переходе не нужно никому. Поправить формулировку: «перезапускала бы эффект и
давала лишнее чтение на каждую смену дня», а не «без конца». Это то же правило — комментарий
должен быть проверяемым.

## Поправка к разделу «A. `recurrence.ts` и `daysInMonth`»

Выше написано, что модуль после `282340f` не менялся. **Это неверно, проверил по истории:**
