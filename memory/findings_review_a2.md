## A2-1. Исправление Н-1 неполное: отказ записи, пришедший ПОСЛЕ смены дня, снова висит под чужим днём

**Важность:** важная

**Где:** `src/routes/CalendarScreen.svelte:202-208` и `src/routes/CalendarScreen.svelte:307-314`

**Что не так.** Правка закрыла только тот порядок событий, при котором `toggleError` уже стоял
к моменту смены дня. Само `toggleCompletion` осталось без защиты от устаревания: между
`await taskRepository.setCompleted(...)` и присваиванием `toggleError` пользователь успевает
выбрать другой день, и сообщение об отказе записи для дня A появляется под списком дня B.
Это ровно тот дефект, который коммит объявил закрытым («сообщение об ошибке отметки висело под
списком другого дня; теперь сбрасывается при смене дня»).

**Доказательство.** Сброс живёт только в эффекте списка и срабатывает в момент смены дня:

```
202	  $effect(() => {
203	    const date = calendarState.selectedDate;
204	
205	    void dayReloadToken;
206	
207	    // Сообщение об отказе записи относится к прежнему дню и на новом не показывается.
208	    toggleError = null;
```

А запись сообщения идёт из асинхронного обработчика, который ни дня, ни поколения не проверяет:

```
307	  async function toggleCompletion(occurrence: Occurrence, done: boolean): Promise<void> {
308	    try {
309	      await taskRepository.setCompleted(occurrence.task.id, occurrence.date, done);
310	      dayReloadToken += 1;
311	    } catch {
312	      toggleError = 'Не удалось сохранить отметку.';
313	    }
314	  }
```

Порядок, дающий дефект: щелчок по флажку дня A → `setCompleted` ещё в полёте → пользователь
нажимает день B → эффект строк 202-208 обнуляет `toggleError` → `setCompleted` отклоняется →
строка 312 ставит сообщение заново, и оно рисуется под списком дня B
(`CalendarScreen.svelte:402-404`, блок внутри `{#if calendarState.selectedDate !== null}`).
Отказ записи в IndexedDB — не мгновенная операция (нехватка квоты, `blocked` при открытой
второй вкладке), так что окно измеряется не микросекундами.

Второе следствие того же отсутствия проверки: успешная запись отметки дня A, пришедшая после
перехода на день B, выполняет `dayReloadToken += 1` (строка 310) и перечитывает день B без
всякой причины — та самая лишняя работа, ради избавления от которой счётчики разделили.

**Что сделать.** Запомнить день в момент щелчка и сверить перед присваиванием — например, сравнить
`occurrence.date` с `calendarState.selectedDate` (или завести счётчик поколений, как `cancelled`
в эффектах) и на несовпадении ни сообщение не ставить, ни `dayReloadToken` не трогать.

а экран опирается на другое.

## A2-4. Дополнение года нулями защищает вход, которого приложение не порождает; настоящий источник непаддингованных годов остался нетронутым

**Важность:** замечание

**Где:** `src/lib/tasks/recurrence.ts:30-32, 44-51` против `src/lib/date.ts:36` и
`src/routes/CalendarScreen.svelte:275-277`

**Что не так.** Регрессия Н-3 первого раунда исправлена внутри `recurrence.ts` (обычные годы не
поехали — это подтверждено перебором 2 315 190 сравнений, см. раздел выше). Но единственная
функция проекта, которая вообще собирает строку даты из числа, год не дополняет:

```
36	  return `${date.getFullYear()}-${pad(date.getMonth() + 1)}-${pad(date.getDate())}`;
```

Поэтому вход вида `0026-01-01`, ради которого добавлен `pad(year, 4)`, приложение создать не
может; оно создаёт `26-01-01`, а на такой строке `parts` даёт `Number('26-0') === NaN`
(`recurrence.ts:36`). Выбор года при этом ничем не ограничен:

```
275	  function shiftYear(delta: number): void {
276	    pickerYear += delta;
277	  }
```

Что при этом происходит фактически (проверено по коду, в браузере не воспроизводил): на годах
меньше 1000 `dayNumber(from)` даёт `NaN`, условие цикла `NaN <= lastNumber` ложно с первого шага
(`recurrence.ts:123`), сетка молча остаётся без меток, а щелчок по ячейке ничего не выбирает —
`calendarState.select` отбивает строку проверкой `isIsoDate` (`src/lib/calendar-state.svelte.ts:46-48`).
Ни зацикливания, ни падения нет, поэтому это замечание, а не дефект: правка ничего не сломала,
но и заявленную дыру закрыла только в одном из двух мест.

**Что сделать.** Либо привести `toIsoDate` к тому же дополнению года (тогда `pad(year, 4)`
получает смысл), либо ограничить выбор года разумным диапазоном и зафиксировать в документации,
что годы меньше 1000 вне области определения, — и тогда `pad(year, 4)` избыточен.

## A2-5. Две реализации хранилища дают РАЗНЫЙ ответ на одних данных: `search` при выдаче больше лимита

**Важность:** замечание (поиск к интерфейсу ещё не подключён — дефект латентный)

**Где:** `src/lib/tasks/memory-repository.ts:141-145` против `src/lib/tasks/dexie-repository.ts:238-246`

**Что не так.** Первый раунд записал по этому пункту «расхождений в значениях не нашёл»
(`memory/findings_review_a1.md:146`). Расхождение есть, и оно не в порядке, а в составе выдачи:
в памяти сначала сортируется всё найденное, потом обрезается по лимиту; в Dexie сначала берутся
первые `limit` попаданий в порядке ОБХОДА ИНДЕКСА, и только потом они сортируются.

**Доказательство.** В памяти — сортировка, затем обрезка:

```
141	    const found = [...this.tasks.values()].filter((task) =>
142	      matchesSearchQuery(task.text, task.searchTokens, parsed),
143	    );
144
145	    return sortTasksByDate(found).slice(0, limit).map(MemoryTaskRepository.copy);
```

В Dexie — обрезка курсором, затем сортировка:

```
238	    const found = await this.tasks
239	      .where('searchTokens')
240	      .startsWith(indexKey)
241	      .distinct()
242	      .filter((task) => matchesSearchQuery(task.text, task.searchTokens, parsed))
243	      .limit(limit)
244	      .toArray();
245
246	    return sortTasksByDate(found);
```

Курсор `where('searchTokens').startsWith(indexKey)` идёт по multiEntry-индексу, то есть в порядке
строк токенов и первичного ключа, а не по дате. Пример на одних данных: `limit = 1`, две задачи
подходят под «молоко», у одной токен «молоко» и дата 2026-12-31, у другой «молокозавод» и дата
2026-01-01. В памяти вернётся задача с датой 2026-01-01 (она первая по `sortTasksByDate`), в Dexie —
задача с токеном «молоко», потому что её ключ в индексе меньше и курсор доходит до лимита раньше.
Расхождение возникает ровно тогда, когда попаданий больше `limit` (по умолчанию 20).

Оговорка: расхождение выведено из кода, в браузере не воспроизводилось — Dexie автотестами
не покрыт по правилу проекта, а поиск ни на одном экране пока не вызывается (`grep` по
`\.search(` вне тестов даёт только сами объявления методов). Порядок обхода multiEntry-индекса —
свойство IndexedDB, а не догадка, но фактическим прогоном оно здесь не подтверждено.

**Что сделать.** Привести реализации к одной семантике: либо в Dexie снимать лимит с курсора и
обрезать после `sortTasksByDate`, либо явно записать в контракт `TaskRepository`, что при выдаче
больше лимита состав ответа не определён, и тогда из документации убрать обещание «поведение
повторяет MemoryTaskRepository» (`dexie-repository.ts:4`).

## A2-6. В Dexie одно и то же вхождение задачи делится объектом `task` между всеми своими днями, в памяти — нет

**Важность:** замечание

**Где:** `src/lib/tasks/dexie-repository.ts:158-162` против `src/lib/tasks/memory-repository.ts:38-44, 73-77`

**Что не так.** В памяти каждое вхождение получает свою копию задачи, и это сделано намеренно —
«вызывающий код может незаметно поменять сохранённые данные» (`memory-repository.ts:26-27`).
В Dexie все вхождения одной регулярной задачи в диапазоне ссылаются на ОДИН объект:

```
158	    for (const task of recurring) {
159	      for (const date of occurrencesInRange(task.date, task.recurrence, from, to)) {
160	        occurrences.push({ task, date, done: done.has(`${task.id}|${date}`) });
161	      }
162	    }
```

Поэтому правка `occurrences[0].task.text` в Dexie изменит текст и у пятого вхождения той же
задачи, а в памяти — нет. Базе это не угрожает: `toArray()` отдаёт свежие объекты, в IndexedDB
они не записываются. Но это наблюдаемое расхождение поведения двух реализаций на одних данных,
и обещание «Поведение повторяет MemoryTaskRepository» (`dexie-repository.ts:4`) оно нарушает.
Сейчас никто вхождения не мутирует, поэтому замечание, а не дефект; риск появится, когда экран
начнёт править задачу на месте (для `$state`-прокси Svelte 5 это как раз естественный соблазн).

**Что сделать.** Либо копировать задачу в Dexie так же, как в памяти, либо записать в контракт
`TaskRepository`, что возвращённые вхождения только для чтения, и держать `readonly` в типах.
