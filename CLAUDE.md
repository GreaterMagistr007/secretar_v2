# Правила проекта Secretar

Язык общения и комментариев в коде: русский. Этот файл переопределяет отдельные пункты глобального `~/.claude/CLAUDE.md`; всё, что здесь не оговорено, действует по глобальным правилам.

## 0. Роль Claude в этом проекте (КРИТИЧНО, указание владельца от 2026-09-13)
- **Зона ответственности Claude — четыре пункта:** чёткое ведение документации · создание агентов под задачи · постановка задач агентам · проверка результатов работы агентов на точное соответствие поставленной задаче и исходной просьбе владельца.
- **Реализацию выполняют агенты.** Claude пишет код сам только там, где заведение агента дороже самой правки (единичная строка, тривиальное исправление), и всё равно фиксирует сделанное в документации.
- **Каждое действие записывается в документацию** — сразу, а не задним числом и не «по итогам этапа». Правки кода, решения, постановки задач агентам, результаты проверок, откаты, найденные факты.
- **Результат агента принимается только после проверки:** сверка с формулировкой задачи, сверка с исходной просьбой владельца, проверка фактической работоспособности. Непроверенный результат выполненным не считается.
- Отчёт владельцу даётся один раз по завершении этапа; промежуточных отчётов о правках нет.
- Подробности режима работы — [docs/rules_work.md](docs/rules_work.md).

## 1. Документация и память

### 1.1 Два хранилища, их назначение (КРИТИЧНО)
- **`docs/` — документация проекта:** цели, требования, решения, правила, архитектура, механики, справочное. Постоянное хранилище.
- **`memory/` — временная память Claude:** промежуточные записи и отчёты агентов, черновики, промпты сессий, наблюдения о работе инструмента. Потеря содержимого не должна стоить проекту ничего.
- **Граница жёсткая:** решение, требование, правило или архитектурный вывод в `memory/` не хранится — им место в `docs/`.
- Оба каталога коммитятся: проект ведётся с разных устройств, доступ к документации — только через репозиторий.
- **Запрещено хранить информацию проекта в глобальной памяти Claude** (`~/.claude/projects/...`) — переопределяет глобальную инструкцию.
- **Оба каталога — вне `.claude/`:** любой путь внутри `.claude/` Claude Code считает чувствительным и требует подтверждения на каждую правку помимо permission-правил; хуками это не снимается.

### 1.2 Индексы и модульность
- `docs/INDEX.md` — главный индекс документации, обязателен к обновлению при появлении, переносе или удалении файла.
- `memory/MEMORY.md` — короткий индекс памяти, ведёт в `docs/INDEX.md`.
- Одна механика — один файл `docs/mechanic_<name>.md` со всеми разделами. Смешивать механики и заводить монолитные перечни всех моделей или маршрутов запрещено.
- Файл, не помещающийся в контекст целиком, разбивается на части с собственным индексом. Ориентир части — около 20 тысяч токенов (60 тысяч символов).
- **Никогда не читать документацию целиком:** сначала `docs/INDEX.md`, затем только нужные файлы; крупные реестры — точечно через `grep`.

### 1.3 Соглашения по именам файлов
Единственный источник — раздел «Соглашения по именам файлов» в `docs/INDEX.md`; здесь не дублируется, два списка разойдутся.

### 1.4 Как работать с документацией
1. Прочитать `docs/INDEX.md`, затем только файлы под задачу.
2. При изменении кода — сразу обновить соответствующий файл документации.
3. Новая механика — создать `docs/mechanic_<name>.md` и добавить ссылку в индекс.
4. **«Сделано и работает» = «записано в документацию».** Триггер выполнения = триггер фиксации.
5. Указание владельца по коду или процессу — зафиксировать в `docs/`.
6. Решение записано только когда пересмотрены все сводные места, где предмет упомянут: индекс, перечни, метрики, счётчики. Проверять поиском по ключевому слову.

### 1.5 Репозиторий — единственный источник истины (КРИТИЧНО)
Проект ведётся с нескольких устройств. Вся документация и вся память лежат в директории проекта, коммитятся и пушатся. Актуально только запушенное: работа начинается с `git pull`, заканчивается коммитом и пушем. Исключения — `.claude/settings.local.json` и секреты (`.env` и производные).

### 1.6 Единственный источник истории — этот проект (указание владельца от 2026-09-13)
Проект делается с нуля. Документация, решения и код других проектов (включая прежнюю версию «secretar») источником истины не являются и не переносятся сюда. Опираться только на документацию этого репозитория и на прямые указания владельца.

## 2. Git workflow
- Ранний этап: без TASK-ID и feature-веток, коммиты напрямую в `master`. Появится команда или PR-процесс — правило переопределяется.
- Формат: `<type>(<scope>): <сообщение>` на русском. Типы: feat, fix, refactor, test, docs, chore, style.
- Не добавлять Co-Authored-By. Все изменённые файлы — в staging.
- **По завершении каждого очередного этапа коммит и пуш обязательны и выполняются без запроса** (указание владельца от 2026-09-13). Это переопределяет глобальное правило «push только по решению пользователя».

## 3. Процесс работы над задачей
- Сначала план в `docs/plan_*.md`, согласование неясных мест.
- **Любой вопрос владельцу — только вариантами:** перечень вариантов, у каждого плюсы и минусы, отдельно рекомендация с обоснованием. Правило безусловное; варианты подаются текстом, а не инструментом выбора.
- **Номер всегда с расшифровкой** — и в документации, и в переписке: «решение Р-3 (MVP минимальный)», «вопрос В-1 (суть проекта)». Голый номер запрещён.
- Не переспрашивать решённое: перед вопросом проверять реестр решений `docs/product_decisions/00_index.md` поиском, а не по памяти.
- **Чтение и правка любых файлов внутри каталога проекта разрешены без запроса** (указание владельца от 2026-09-13). Подтверждение сохраняется только для секретов, настроек самого Claude Code и разрушительных команд.
- Задача больше 2–3 файлов или крупный анализ — делегировать агенту; основной чат держать чистым.
- Файлы отчётов агентов — в `memory/`, не в `/tmp` и не в scratchpad. Запись — дописыванием через Bash. Имя файла не начинается с `report`. Проверять агента не реже раза в 3 минуты; ожидание завязывать на завершение агента, а не на появление файла.

## 4. Обязательные правила при изменении кода
1. Любое изменение фиксируется в документации механики. Без исключений.
2. Проверить работоспособность до отчёта: нерабочий код и 500-ошибки недопустимы.
3. Не оставлять TODO, FIXME, заглушек — реализовывать полностью либо явно сообщить, что осталось.
4. Изучать существующие паттерны проекта и следовать им.
5. Предупреждать о breaking changes.

## 5. Объём работ (указание владельца от 2026-09-13)
MVP берётся минимальным, функционал наращивается постепенно. В работу попадает только то, что можно сделать здесь и сейчас; охватывать всё сразу запрещено. Всё остальное — в `docs/backlog_post_mvp.md` с триггером возврата.

## 6. Качество кода
SOLID, DRY, KISS, строгая типизация где возможно, комментарии на русском для сложной логики, PHPDoc/JSDoc для публичных API. Правила стека — `docs/code_style.md`. **Перед пушем — агент-скептик:** чистота кода, соответствие комментариев коду, соответствие задаче, отсутствие регрессий.

## 7. Тесты
- Код покрывается автотестами; по завершении механики — полный прогон и проверка покрытия.
- **Автотесты не обращаются к базам данных вообще.** Данные хардкодятся в тесте, зависимости мокаются. Фикстуры, миграции в тестах, `Schema::*`, truncate и insert запрещены.
- Перед любыми операциями записи, удаления или смены схемы — проверять фактическое соединение (драйвер, host, database), не доверяя конфигам. Ни dev, ни prod, ни локальные базы не должны пострадать. При сомнении — остановиться и спросить.

## 8. Логирование и узкие места
При написании механики — предлагать покрытие логами. Сообщать об узких местах; нашёлся способ обойти или сломать механику — описать кейс и предложить решение. По завершении механики — тест-кейсы для dev и prod.

## 9. Окружение и деплой
- Стек не выбран — открытый gate, см. `docs/tech_stack.md`. Первый этап: PWA-прототип.
- Умолчание по среде: вся серверная инфраструктура — в docker-контейнерах (приложение, база, веб-сервер, обработчики очередей, планировщик), файлы сборки и оркестрации в репозитории, поднятие одной командой, платформенно-зависимого кода нет. Окончательная конфигурация фиксируется при закрытии gate по стеку — вопрос В-3 (конфигурация docker-среды).
- Деплой — в отдельную директорию с очередным порядковым номером, хранить последние 5 релизов; откат контейнерный. Инфраструктурные изменения — сразу в `docs/infra_*.md`, `docs/deployment.md`.
- **Claude никогда не деплоит.** Работа доводится до коммита и пуша.

## 10. Прочее
Разрешения проекта заданы в `.claude/settings.json` (коммитится): внутри каталога проекта чтение и правка файлов выполняются без лишних запросов; подтверждение сохраняется для секретов (`.env*`, `.ssh`, ключи, credentials), настроек самого Claude Code и разрушительных команд (`rm`, `shred`, `truncate`, `mv`, `git reset --hard`, `--delete`). Зависимость хуков — `jq`. Правка этого файла в идущей сессии не действует до `/hooks` или перезапуска. Запись в него блокируется режимом auto mode (причина `[Self-Modification]`) — править из режима `accept edits`, см. вопрос В-4 (создание `.claude/settings.json`).
Не коммитить `.env`, credentials, токены, ключи; предупреждать при обнаружении секретов. Новые env-переменные — в `.env.example`. Перед добавлением зависимости — проверить аналог и обосновать. Новые каталоги — по согласованию. Применённые миграции не редактировать. Стиль ответов: без эмодзи, без извинений, без воды.
