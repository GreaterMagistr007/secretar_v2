# Реестр вопросов

Статусы: `решено` · `в работе` · `в очереди` · `отложено` · `этап реализации`. Решённый вопрос переносится в реестр решений `product_decisions/00_index.md` со ссылкой на номер решения. Ссылаться на вопрос только с расшифровкой: «вопрос В-1 (суть проекта)».

Экранов в MVP четыре (календарь, задача, настройки, выбор темы) — формулировка «три экрана» отменена вместе с редакцией решения Р-11 2026-09-27. Зафиксировано решениями Р-11 (суть MVP), Р-12 (главная цель — дизайн), Р-13 (форма поставки PWA на GitHub Pages); развёрнуто в `product_goals.md`, `product_scope/00_index.md`, `req_tasks.md`, `req_screens.md`.

## В-5. Условия публикации на GitHub Pages
**Статус:** решено и выполнено 2026-09-13.
Исходная проблема: репозиторий `GreaterMagistr007/secretar_v2` был приватным (`private: true`), план аккаунта — `free`, `GET /repos/.../pages` → 404. На тарифе `free` GitHub Pages работают только для публичных репозиториев, поэтому выбор стоял между публичным репозиторием, оплатой GitHub Pro и сторонним хостингом. Владелец выбрал публичный репозиторий.
**Выполнено владельцем и проверено через GitHub API 2026-09-13:** `private: false`, `visibility: public`, `has_pages: true`; Pages настроены на `build_type: workflow` (Source — GitHub Actions), адрес сайта `https://greatermagistr007.github.io/secretar_v2/`. Публикаций ещё не было (`status: null`) — первая пойдёт с первым пушем собранного приложения.

## В-6. Маршрут создания задачи из календаря
**Статус:** решено 2026-09-27 владельцем — решение Р-27 (создание кнопкой «+», дата из выбранного дня).

## В-7. Устройство экрана «Календарь»
**Статус:** порядок выбора согласован 2026-09-27 — решение Р-28 (владелец выбирает из трёх отобранных кандидатов); сам выбор ещё не сделан.

Claude отбирает из 30 макетов галереи трёх кандидатов по читаемости и плотности сетки с обоснованием, владелец выбирает один. Триггер: отбор выполняется после этапа повторений и отметок выполнения.

## В-8. Перенос повторения при отсутствующей дате
**Статус:** решено 2026-09-27 владельцем — решение Р-25 (перенос на последний день месяца).
Ежемесячная задача с датой старта 29, 30 или 31 числа в коротком месяце попадает на последний день месяца; ежегодная задача с 29 февраля в невисокосный год — на 28 февраля. Повторение не пропускается.

## В-4. Создание `.claude/settings.json` с разрешениями и хуками проекта
**Статус:** решено 2026-09-13, файл создан и проверен.
Файл задаёт `defaultMode: acceptEdits`, правила `Edit/Write/NotebookEdit(./**)` и три хука (`PreToolUse` для правок файлов, `PreToolUse` для Bash, `PermissionRequest`) — техническая реализация решения Р-9 (правка файлов проекта без запроса).
**Как решилось:** первые попытки записи — через Bash и через инструмент `Write` — были отклонены классификатором режима auto mode с причиной `[Self-Modification]`; наличие `Bash(*)` в глобальном `permissions.allow` от отказа не спасло. Владелец переключил режим сессии на `accept edits`, после чего файл записался обычным способом. Вывод: запись в настройки Claude Code блокируется именно режимом auto mode, а не permission-правилами.
**Проверено фактическим прогоном хуков** (`jq` 1.7, JSON валиден): правка файла проекта — `allow`; `.env` — исключение, решение остаётся за обычным подтверждением; команда `ls docs` — `allow`; `rm -rf docs` и `cat .env` — исключения; `PermissionRequest` на файл проекта — `allow`.
**Важно:** хуки кэшируются на момент старта сессии — в текущей сессии файл не действует до `/hooks` или перезапуска.

## В-9. Политика контраста тем
**Статус:** решено 2026-09-27 владельцем — решение Р-26 (поднимать только пары ниже 3,0:1).

Измерение по всем 30 темам (см. таблицу в `mechanic_themes.md`): основной текст читается везде, но приглушённые подписи, числа выходных, неактивные вкладки и часть акцентных кнопок ниже порога 4,5:1, худшее значение 1,90. ## В-11. Освежение сегодняшнего дня в долгоживущем экране календаря
**Статус:** решено 2026-09-27 по ходу саморевью, вопрос владельцу не выносился — выяснилось, что это не оформление, а порча данных.
Исходно казалось косметикой: в установленной PWA экран календаря живёт без перезагрузки, и после полуночи подсветка текущего дня отставала на день. Ревью показало, что через выбранный день это доходит до данных: выбор дня тоже переживает полночь, `aria-current` продолжает называть вчерашнее число сегодняшним, и нажатие «+» утром сохраняло задачу на вчера — при том что правки задачи в интерфейсе нет (требование Т-28).
**Решение:** экран календаря сам следит за сменой суток и не даёт устаревшей дате попасть в новую задачу. Механизм здесь намеренно не пересказывается — он уточнялся четырьмя раундами саморевью, и пересказ в этом документе успел разойтись с кодом трижды. Как именно сделано и что проверено — [mechanic_tasks.md](mechanic_tasks.md), раздел про экран календаря; он и есть источник истины по реализации.

## В-12. Два способа проверять данные задачи
**Статус:** в очереди, требуется решение владельца.
В проекте два независимых способа проверить введённое в форме: модуль `src/lib/tasks/validate.ts` (`validateNewTask`, 38 тестов) и собственные `$derived`-проверки внутри модалки создания. Приложение вызывает только вторые — `validateNewTask` не вызывается ниоткуда, кроме тестов. Заодно проверка даты существует дважды: `isCalendarDate` в валидаторе и `isIsoDate` в модуле дат. Расхождение появилось до этапа повторений, обнаружено саморевью 2026-09-27.
Варианты: **подключить валидатор в модалку** и убрать дублирующие проверки — плюс: один способ вместо двух, 38 тестов начинают защищать рабочий путь; минус: правка работающей формы без запроса пользователя, риск задеть поведение кнопки сохранения · **удалить валидатор** — плюс: минус мёртвый код и 38 тестов, которые проверяют недостижимое; минус: теряется готовая проверка, которая понадобится при импорте данных и при серверной части (решение Р-22) · **оставить как есть, записав причину** — плюс: ноль работы; минус: правило «не заводить второй способ делать то же самое» нарушено осознанно и надолго.
**Рекомендация:** первый вариант, но отдельной задачей и не вместе с другими правками формы: он делает проверку одной и сразу даёт тестам смысл.

## В-13. Покрытие тестами роутера и состояния календаря
**Статус:** в очереди, требуется решение владельца.
Правило проекта требует юнит-тесты для каждого модуля с логикой. `src/lib/router.svelte.ts` (разбор адреса, раскодирование идентификатора) и `src/lib/calendar-state.svelte.ts` (проверка даты, сверка суток) логику содержат и не покрыты ничем: файлы `*.svelte.ts` из-за руны `$state` не исполняются в тестовом окружении без плагина Svelte, и в измерение покрытия они не входят. Записано в «Известные границы» механики 2026-09-27.
Варианты: **вынести чистую логику в обычные модули** по образцу `isStaleSelection`, оставив в `*.svelte.ts` только хранение — плюс: логика покрывается, класс дефектов «руна мешает тестам» закрывается насовсем; минус: правка двух работающих модулей и новые файлы · **подключить плагин Svelte к тестовому стенду** — плюс: тестировать можно всё как есть; минус: тесты начинают тянуть сборочные плагины, чего конфигурация избегала намеренно, и стенд усложняется · **оставить, границы записаны** — плюс: ноль работы; минус: в этих двух модулях пять раундов ревью подряд находили дефекты, и именно они остаются без автоматической защиты.
**Рекомендация:** первый вариант. Он уже один раз сработал: вынесенная проверка устаревания выбора покрыта тестами и поймала бы тот дефект, который искали вручную.

## В-14. Правка и удаление задачи в интерфейсе
**Статус:** в очереди, требуется решение владельца.
Сейчас задачу можно создать, посмотреть и отметить выполненной. Изменить текст, дату, приоритет или повторение нельзя, удалить — тоже: требование Т-28 описывает экран задачи как просмотр, требования на правку нет. Хранилище это умеет (`update`, `remove` с каскадом отметок), интерфейса нет. Ошибку в сохранённой задаче исправить нечем — это уже всплывало в разборе дефектов с датой.
Варианты: **добавить правку и удаление на экран задачи** — плюс: ошибку можно исправить, а не завести заново; минус: новое требование, форма правки, и при переносе даты у регулярной задачи прежние отметки могут «ожить» (записано в архитектуре) · **только удаление** — плюс: дешевле всего, ошибочную задачу можно убрать; минус: править всё равно нечем · **оставить как есть** — плюс: минимальный MVP по решению Р-3; минус: задачник, в котором нельзя исправить опечатку, на реальных данных раздражает.
**Рекомендация:** второй вариант сейчас, первый — когда будет решён вопрос В-7 и раскладка экрана перестанет быть временной: форму правки разумно рисовать уже в итоговом дизайне.
