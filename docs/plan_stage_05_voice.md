## Локальная модель: итог исследования и ревью скептика (2026-11-21)
Источники: `memory/findings_voice_audio_llm.md` (исследование), `memory/findings_skeptic_voice_audio.md` (ревью, находки С-1…С-15). Ключевые утверждения скептика постановщик проверил сам: `toolChoice` в `Conversation.kt` тега v0.19.1 отсутствует, в main есть (строка 128); «до ~10 секунд» на `Engine.initialize()` — `Engine.kt:55` v0.19.1; `gated: False`, `apache-2.0` (API HF); порог `minDeviceMemoryInGb: 8` для E2B в списке моделей Google AI Edge Gallery 1.0.23.
- **Кандидат — Gemma 4 E2B на LiteRT-LM 0.19.1** (`gemma-4-E2B-it.litertlm`, 2 588 147 712 байт, Apache 2.0, открыт без авторизации). Единственная найденная связка, где подтверждены звук на входе, структурированный ответ, Android minSdk 24, arm64-v8a и x86_64. Звук — 16 кГц моно, до 30 с. Остальные модели со звуком отброшены: нет русской речи (Voxtral Mini, Phi-4-multimodal, LFM3-Omni), лицензия только для исследований (Qwen2.5-Omni), размер (MiniCPM-o), хуже по всем пунктам (Gemma 3n).
- **Качество русской речи у Gemma 4 не измерено нигде** — главный риск; меряется только своим набором фраз.
- **Вызов инструмента — ответом по JSON-схеме.** Принудительного вызова инструмента (`ToolChoice.Required`) в выпущенной 0.19.1 нет (С-1); вместо него `ResponseFormat.json(схема add_task)` с `enableResponseFormat = true`, без инструментов (с включёнными инструментами схема молча отбрасывается). Для веб-части результат тот же — объект аргументов `add_task`.
- **Модель в APK не помещается** (С-5): даже без зрения и MTP-драфтера 2,31 ГБ при пределе 2 ГиБ; рантайм принимает только путь к файлу, так что модель из APK всё равно копировалась бы (двойной расход места). Модель — отдельный файл в `filesDir` приложения.
- **Плагин — на Java** рядом с `TaskNotifierPlugin` (С-6): API LiteRT-LM вызывается из Java без корутин; Kotlin-зависимости библиотеки приходят транзитивно, Kotlin-плагин Gradle не нужен (конфликт версий `kotlin-stdlib` с Capacitor 8 — проверить первой сборкой).
- **Устройство:** текстовая часть — GPU с откатом на CPU, аудиоэнкодер (94 МБ) жёстко на CPU (С-4); жадное декодирование (`SamplerConfig(1, 1.0, 0.0)`), размышление выключено, `maxOutputToken` около 128 (С-12); системный промпт с датой считается один раз (`prefillPrefaceOnInit`), на каждое нажатие — `clone()` разговора (С-9); загрузка модели — до ~10 с, поэтому модель держится загруженной, пока приложение открыто, и выгружается при сворачивании (точный момент — после замера, С-9).
- **Запись — нативно** (`AudioRecord`, 16 кГц моно PCM16 → WAV во временный файл), сигнал готовности после фактического старта записи (вибрация или вид кнопки), обрезка на 30 с, слишком короткое нажатие в модель не отправляется (С-10).
- **Требование к телефону:** Google ставит для E2B порог 8 ГБ ОЗУ, для E4B — 12 ГБ (С-7).
- **Запасной путь** — два шага офлайн: GigaAM v3 (0,16 ГБ) распознаёт, Gemma 4 E2B разбирает текст; отступает от Р-34, применяется только с согласия владельца.

Порядок экспериментов (замена прежнего «Порядка реализации» для этапов 1–7):
1. Ответы владельца: телефон, смысл «встроена в приложение», критерий годности модели.
2. Хост, без Android: 20–30 фраз голосом владельца → Python-API `litert-lm-api` 0.19.2 в docker на том же файле модели; E2B и E4B, ответ по JSON-схеме; для сравнения — двухшаговый путь. Итог — таблица «фраза → разбор, верно/неверно». Скорость хоста к телефону не относится, качество — относится.

## Ускорение по журналу №2 (2026-11-22)
Картина «до» на телефоне владельца (`memory/findings_voice_phone_log_2.md`, GPU): чтение промпта 1000 токенов — 3,8 с; звук — 0,8 с; ход со звуком — 0,6–1,1 с; генерация 45–55 токенов — 5–6 с (9 ток/с); ответ модели 10,3–12,3 с. GPU телефона генерирует вдвое медленнее CPU компьютера. По цели владельца «предельно ускорить» в APK 8 делается всё, что замеры показали безопасным для качества (`memory/findings_voice_speed_host.md`):
1. Постоянная часть промпта (правила, календарь, инструмент) читается один раз при загрузке модели и при смене дня (полночь и 4:00 — ночное правило); на нажатие — копия готового разговора (`clone()`), в сообщении пользователя — только текущее время и звук. Ожидаемо −3,8 с.
2. MTP-драфтер (`speculativeDecodingConfig` ON) с откатом на OFF, если не запустится. Ожидаемо генерация ×1,65–2,5.
3. Окно контекста 4096 → 2048.
4. Выбор устройства для модели в «Настройки → Голос»: GPU (по умолчанию) или CPU — для сравнения на телефоне владельца, раз его GPU медленный.
Цель — ответ модели около 3 с. Всё пишется в журнал (время копии разговора, пересборка промпта, режим MTP и его статистика, устройство).

- **ОТМЕНЕНО владельцем 2026-11-22 после журнала APK 8: одна фраза — одна задача** (ход «Готово» стоил 2 с на каждом нажатии). Прежний пункт: **Несколько задач из одной фразы** (выбор владельца 2026-11-22, вариант «б»): «во вторник и в среду заехать в берёзовый» — две задачи. Промпт разрешает несколько вызовов `add_task` (по одному на каждую задачу или день); сохраняются все верные вызовы; сообщение перечисляет добавленные; неверные вызовы — в журнал, а если верных нет — ошибка. Цена известна владельцу: ответ модели длиннее.

- **Ночью «сегодня» — ближайшее будущее** (уточнение владельца 2026-11-22 к Р-38, ответ на находку Ск-9): «если „сегодня“ считается с 4 часов ночи, то „сегодня в 3“ — это 15:00 сегодняшнего дня»; поля времени у задачи нет, поэтому важен только день. Примеры владельца: в 03:00 «завтра в 4» → этот же календарный день; в 03:00 «сегодня в 4» → этот же календарный день. Итог правила до 4:00 (календарный день D): «сегодня» (с временем и без) → D, «завтра» → D, «послезавтра» → D+1, дни недели — от D−1 (как раньше), день не назван → D. Прошедший день не получается никогда. Сверка `chrono-node` ночью: дата, равная D−1, приводится к D.

- Решения владельца 2026-11-22: **сокращение системного промпта отложено до журнала APK 8** (после переноса постоянной части в кэш его длина на нажатие почти не влияет); **«через N дней» ночью — оставить, как модель считает сейчас (от текущего календарного дня)**, править только по жалобам пользователей (бэклог).

- **Приоритет `chrono-node` на «сегодня/завтра/послезавтра»** (выбор владельца 2026-11-22, вариант «б»): если `chrono-node` нашёл в услышанной фразе слово «сегодня», «завтра» или «послезавтра» и его дата расходится с датой модели, задача сохраняется по дате `chrono-node` (с ночным правилом); в журнал — обе даты и источник. Причина: модель на слух путает «в пять» с «в пятницу» («Сегодня в пять забрать машину» → 27.11). Уточняет выбор 5.2 (модель считает, `chrono-node` сверяет).

- **Короткое время** (выбор владельца 2026-11-22, варианты «а» + «б» по опыту `memory/findings_voice_time_hearing.md`): запись продолжается 300 мс после отпускания кнопки (последнее слово не обрезается); время называть полнее («в семь утра», «в 7 часов», «в три часа дня») — промпт не меняется, «в семь» модель слышит как «всем» при любой формулировке.

- Тесты идут в окружении node, руны `$state` там не исполняются (`vitest.config.ts`, `src/lib/date.ts`) — логика должна быть на чистом TS.
- Правки и удаления задачи в интерфейсе нет (вопрос В-14 (правка и удаление задачи) открыт).
- В APK уже есть свой Java-плагин `TaskNotifier`. Разрешения `RECORD_AUDIO` в манифесте нет. Серверной части нет (решения Р-22, Р-23 — на будущее).
- PWA живёт на общем адресе `greatermagistr007.github.io` вместе с другими сайтами владельца: хранилище браузера (localStorage, IndexedDB) делится по адресу, а не по пути — их скрипты читают данные «Секретаря».

## Ключевые факты исследований (2026-11-21)
- Claude API звук на вход не принимает (документация platform.claude.com). При разборе фразы Claude распознавание — отдельный шаг.
- Web Speech API: Chrome на Android и десктопе, Safari — да; Firefox на Android — нет. Только онлайн (облако Google), офлайна нет. Внутри Android WebView (наш APK) по исходникам Chromium поддерживается, если в манифесте есть `<queries>` с `android.speech.RecognitionService`, разрешения `RECORD_AUDIO` и `MODIFY_AUDIO_SETTINGS` и на телефоне есть сервисы Google; есть противоречащий отчёт стороннего проекта (ноябрь 2026).
- Нативный распознаватель Android работает без окна; офлайн — только на Android 12+ (API 31) в режиме распознавания на устройстве со скачанным языковым пакетом. Без сервисов Google (Huawei, часть китайских прошивок) распознавателя может не быть.
- Плагины Capacitor 8: `@capgo/capacitor-speech-recognition` 8.6.0 (2026-11-17, MPL-2.0, большой код с многими режимами); `@capacitor-community/speech-recognition` под Capacitor 8 не выпущен. Свой Java-плагин — оценка 150–220 строк.
- Облачное распознавание: OpenAI `gpt-4o-mini-transcribe` $0.003/мин, Deepgram Nova-3 $0.0043/мин, Yandex SpeechKit 0,16 ₽ за фразу (без CORS).
- Локальное распознавание: Vosk small-ru 45 МБ, ошибки в 12–32 % слов; GigaAM v3 (Сбер) через sherpa-onnx ~163 МБ, MIT, лучшее качество русского среди открытых, готового плагина Capacitor нет.
- Локальная ИИ на телефоне: Gemini Nano — бета, только флагманы, русский не подтверждён, строгий формат только из Kotlin. Gemma 4 E2B (LiteRT-LM) — официальный вызов функций, 2,58 ГБ, замеров на среднем телефоне и на русском нет. llama.cpp + Qwen 0,4–2,5 ГБ; модели до 2B в замере вызова функций BFCL-V4 — 10–14 баллов, Qwen3.5-4B — 50,3. WebGPU в Android WebView не подтверждён.
- Облачная ИИ: обращение (~700 токенов вход, 100 выход) стоит доли цента у всех: Claude Haiku 5.5 ≈ $0.00012, Gemini Flash-Lite ≈ $0.00011, Alice AI LLM Flash ≈ 0,09 ₽, GigaChat Lite ≈ 0,05 ₽ (физлицам 250 млн токенов бесплатно на 12 месяцев).
- CORS (проверено предзапросами): Anthropic, OpenAI, Gemini разрешают вызов из браузера; Yandex и GigaChat — нет. В APK CORS обходится нативным HTTP `CapacitorHttp` из уже установленного `@capacitor/core` — без новой зависимости. У GigaChat ещё сертификат НУЦ Минцифры, которому Android не доверяет.
- Россия: Anthropic, OpenAI, Google Gemini её в поддерживаемых странах не имеют; условия Anthropic учитывают физическое местонахождение пользователя — использование из России грозит блокировкой аккаунта. Yandex и Сбер работают из России с оплатой в рублях.
- `chrono-node` 2.10.3 знает русский, но ошибается на «в 12 часов» (22:00), не связывает время с днём в «в понедельник маникюр в 12», не понимает «каждый понедельник».

### Этап 1. Кнопка «слушать» и машина состояний
Положение — по постановке: центр нижнего ряда, тот же `bottom`, что у «+», размер 56×56.

Уход с экрана календаря или сворачивание приложения во время прослушивания — прослушивание прерывается, микрофон освобождается; во время запроса к ИИ — запрос довершается, сообщение показывается (оно живёт в `App.svelte`).

### Этап 5. Системный промпт
Передаётся: дата `YYYY-MM-DD`, день недели по-русски, время `HH:MM`, часовой пояс, таблица ближайших 14 дней («2026-11-23 — понедельник» …), правила, примеры.
Как получить верную дату:
- **5.1 Модель считает сама по таблице дней.** Плюсы: просто; таблица снимает с модели арифметику календаря. Минусы: ошибка модели возможна, хоть и маловероятна.
- **5.2 Модель возвращает дату, код сверяет с `chrono-node`.** Плюсы: страховка. Минусы: новая зависимость, `chrono-node` сам ошибается — ложные отказы.
- **5.3 Модель возвращает относительное выражение, дату считает код.** Плюсы: арифметика детерминирована. Минусы: схема сложнее, редкие выражения теряются.
- **Рекомендация: 5.1** и проверка кодом: дата в прошлом (относительно `todayIso()`) или дальше 5 лет — `error` с этой датой, задача не создаётся.
Правила промпта (решаются по умолчанию, без вопроса):
- «В понедельник» — ближайший следующий понедельник, сегодняшний не считается — по формулировке владельца «следующий ближайший». Дата и день недели всегда видны в сообщении об успехе.
- Время переносится в текст так, как сказано («Маникюр в 12», «Маникюр в 7 вечера»), без перевода в 24-часовой формат: «в 12» — полдень или полночь, угадывать нельзя. Время без дня — сегодня.
- Повторения: «каждый день/неделю/месяц/год», «каждый понедельник» (`weekly` с датой ближайшего понедельника); неподдерживаемые («по будням», «каждые две недели») — инструмент не вызывать, `error` «Такое повторение пока не поддерживается».
- Приоритет: «важно», «срочно» → `high`; «не срочно», «когда-нибудь» → `low`; иначе `medium`.
- Фраза не про новую задачу — инструмент не вызывать. `tool_choice: auto`: при принудительном вызове модель создаст задачу даже из «эээ».

### Этап 6. Инструменты (вопрос владельца 3)
Сейчас один — `add_task`: `text` (обязательный, до 200 символов), `date` (`YYYY-MM-DD`), `priority` (`low` | `medium` | `high`), `recurrence` (`none` | `daily` | `weekly` | `monthly` | `yearly`). Строгая схема; аргументы проходят существующую `validate.ts` и проверку диапазона даты, сохраняются **через тот же `createTask`**, что и ручное создание: уведомление дня, выбор дня, сетка и список обновятся сами. Другие команды (отметить выполненной, прочитать задачи дня, перейти к дню) — в бэклог.
Время «в 12»:
- **6.1 Время в тексте:** «Маникюр в 12». Плюсы: модель данных не меняется, сказанное не теряется. Минусы: по времени нельзя сортировать и напоминать.
- **6.2 Поле времени у задачи** (схема Dexie, форма, список, сортировка, уведомление). Плюсы: полноценно. Минусы: отдельная крупная механика.
- **6.3 Отбрасывать время.** Минусы: теряется сказанное. Не рекомендуется.
- **Рекомендация: 6.1;** 6.2 — отдельным решением владельца.
Сохранять ли сразу:
- **6.4 Сразу сохранять и показать сообщение** — по постановке. Плюсы: одно действие. Минусы: удалить ошибочную задачу нельзя — в интерфейсе нет ни правки, ни удаления (В-14), а задача на сегодня попадёт и в постоянное уведомление.
- **6.5 Открывать заполненную форму для подтверждения.** Плюсы: ошибка видна до сохранения. Минусы: лишнее касание, расходится с постановкой.
- **6.6 Сохранять сразу + «Отменить» в сообщении об успехе.** Плюсы: ошибка исправляется одним касанием. Минусы: за 3 секунды попасть трудно, сообщение придётся сделать нажимаемым.
- **Рекомендация: 6.4** (постановка владельца) и поднять вопрос В-14 (правка и удаление задачи) следующим этапом — он нужен и без голоса.

### Этап 7. Итоговое сообщение
- **7.1 Текст собирает код по результату инструмента:** «Добавлено: Маникюр в 12 — пн, 23 ноября». Плюсы: один запрос к ИИ, мгновенно, предсказуемо; ответ модели не выводится — нечему внедряться. Минусы: шаблонная формулировка.
- **7.2 Второй запрос к ИИ — модель формулирует ответ.** Плюсы: живой язык. Минусы: вдвое дольше и дороже, ещё одна точка отказа.
- **Рекомендация: 7.1.** Модель не вызвала инструмент — `error` «Не понял: «…»» с услышанной фразой.

### Этап 8. Всплывающее сообщение
Реализация: свой компонент Svelte (8.1, ~50 строк, без зависимостей). Альтернативы — библиотека `svelte-sonner` (новая зависимость, своя анимация) и нативный Android Toast (нет в PWA, нет типов) — не рекомендуются. Логика (показ, замена, снятие) — чистый TS с внедряемым таймером, руна — тонкая обёртка: иначе тестов не написать. Анимация — CSS `@keyframes`, удаление — по таймеру, а не по концу анимации (тайминги — выбор 8.б, устройство — [mechanic_toast.md](mechanic_toast.md)). Новое сообщение заменяет предыдущее. Контейнер с `aria-live` постоянно в DOM, для ошибки — `role="alert"`. `pointer-events: none` — сообщение не мешает касаниям. При `prefers-reduced-motion` — без затухания, видно весь срок показа и снятие. Место — по центру над нижним рядом кнопок.
Тайминг ошибки — вопрос владельцу (фразу «Не понял: «в понедельник маникюр в 12»» за 1 с не прочитать):
- **8.а Оба типа ровно по постановке** (1 с + 2 с). Плюсы: как задано. Минусы: текст ошибки часто не успевают прочитать.
- **8.б Успех по постановке, ошибка дольше** — например 4 с видно + 2 с тухнет. Плюсы: ошибку успевают прочитать, успех не мешает. Минусы: два тайминга.
- **8.в Оба по постановке, касание останавливает исчезновение.** Плюсы: один тайминг. Минусы: сообщение становится нажимаемым — перекрывает касания по списку.
- **Рекомендация: 8.б.**
Цвета — токенов «успех»/«ошибка» в темах нет:
- **8.4 Без новых токенов:** фон и текст из темы (`--color-surface`, `--color-text`), ошибка — значок и полоса `--color-weekend` (цвет ошибок по всему проекту), успех — значок и полоса `--color-primary`. Плюсы: ни одного нового токена, контраст фона и текста уже проверен (Р-26). Минусы: тип различается значком и полосой, а не заливкой.
- **8.5 Два новых токена во все 30 тем.** Плюсы: точный цвет под тему. Минусы: 60+ значений и замеры контраста ради одного компонента.
- **Рекомендация: 8.4.**

### Этап 9. Ошибки, логи, тесты, проверка
- Сообщения `error`: нет доступа к микрофону · распознаватель недоступен · ничего не услышано · нет сети · нет ответа (таймаут 15 с) · не задан ключ (с подсказкой «Настройки → Голос») · провайдер отказал (ключ, лимит) · не понял · повторение не поддерживается · дата вне диапазона · аргументы не прошли проверку.
- Логи: `console.info` по шагам с длительностью, `console.warn` на ошибках; текст фразы и ключ в логи не пишутся.
- Тесты (без БД и сети, данные в коде теста, фейки распознавателя, клиента ИИ и репозитория): системный промпт (дни недели, переходы месяца и года, понедельник в понедельник), разбор ответа модели (вызов / текст без вызова / отказ / обрыв по лимиту / сеть / таймаут), проверка аргументов и диапазона даты, текст итогового сообщения, тайминг сообщения на фиктивных таймерах, переходы машины состояний, весь конвейер целиком на фейках. Новые модули — в `coverage.include`.
- Проверка: эмулятор `secretar-emu-check` (сначала — умеет ли он микрофон хоста), браузер Chrome для логики, финально — телефон владельца, APK с поднятым `versionCode`.
- Промпт-инъекция: риск низкий — инструмент один и только создаёт задачу, фразу говорит сам пользователь, ответ модели не выводится, `@html` в проекте не используется. Длина текста задачи ограничена 200 символами.
