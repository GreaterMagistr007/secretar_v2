# Механика: голос

Реализована 2026-11-21 по решению Р-36 (модель — отдельный файл, докачивается в «Настройки → Голос» из локальной сети), уточняющему Р-34 (голос — только в APK, офлайн, локальной моделью со звуком на входе). План и выбор владельца — [plan_stage_05_voice.md](plan_stage_05_voice.md), раздел «Выбор владельца 2026-11-21 (2): доставка модели». Голосовая кнопка с журналом — 2026-11-21 по решению Р-37 (сразу рабочая кнопка, каждое нажатие — в журнал), раздел «Голосовая кнопка» ниже. Скачивания модели с Hugging Face из приложения нет.

## Модели
- Каталог — `VOICE_MODELS` в `src/lib/voice-models.ts`, одна запись: `gemma-4-e2b`, «Gemma 4 E2B», файл `gemma-4-E2B-it.litertlm`, 2 588 147 712 байт. Первая запись — модель по умолчанию.
- Веб-часть: `localStorage` — `secretar.voice.model` (id выбранной модели; неизвестный id читается как модель по умолчанию), `secretar.voice.server` (адрес сервера раздачи как введён) и `secretar.voice.device` (устройство для модели `GPU` или `CPU`, с 2026-11-22; нет или неизвестное — `GPU`; `VOICE_DEVICES`, `loadVoiceDevice`/`saveVoiceDevice`). Недоступное хранилище — как у остальных настроек: значение действует в сеансе, но не запоминается.
- Нативная часть: `SharedPreferences` `model_downloader` — `download_id` (номер загрузки DownloadManager) и `file_name`, пусто — загрузки нет; `verified_file` — имя файла, чья загрузка завершилась успешно с верным размером (отметка «проверен»).
- Файл модели на устройстве: `getExternalFilesDir("models")/<имя файла>` = `/sdcard/Android/data/io.github.greatermagistr007.secretar/files/models/`. Почему не `filesDir`: DownloadManager работает в своём процессе и пишет только во внешнее хранилище; каталог приложения во внешнем хранилище не требует разрешений, приватен для приложения на Android 11+ и удаляется вместе с приложением. Рантайм модели принимает путь к файлу, копировать в `filesDir` не нужно.
- **Резервная копия Android:** файл модели (`external`, `models`) и `model_downloader.xml` (`sharedpref`) исключены из Auto Backup и переноса на новый телефон — `res/xml/backup_rules.xml` (Android ≤11) и `res/xml/data_extraction_rules.xml` (Android 12+), см. [mechanic_android.md](mechanic_android.md), «Резервная копия». Без этого модель 2,6 ГБ превышала квоту облачной копии (25 МБ), и копия приложения вместе с задачами не делалась вовсе (проверено на эмуляторе: «Size quota exceeded»). После восстановления или переноса модель скачивается заново.

## Сервисы

### Чистая логика — `src/lib/voice-models.ts`
- `findVoiceModel(id)`, `loadVoiceModel` / `saveVoiceModel`, `loadServerAddress` / `saveServerAddress`.
- `normalizeServerAddress(input)` → `схема://хост[:порт][/путь]` без `/` в конце или `null`: пробелы по краям убираются; без схемы — `http://`; ввод без `://`, похожий на опечатку в схеме или с пустым портом (`http:/x`, `http//x`, `http:x`, `x:/путь`), — неверно: иначе «http» стал бы именем хоста; разбор `URL` (порт вне 1…65535, порт 0, пробел в хосте — неверно); только `http`/`https`; адрес с `?` или `#` — неверно (к нему не приписать имя файла); адрес с именем пользователя или паролем — неверно (раздача их не принимает); IPv6 — только в скобках (`[fe80::1]:8088`); порт по умолчанию схемы опускается (`:80` для http). Порт 8088 сам не подставляется: `http://host` однозначно значит порт 80.
- `modelFileUrl(server, model)` — адрес сервера + `/` + `encodeURIComponent(имя файла)`.
- `formatMegabytes` (десятичные МБ, вниз, разряды неразрывным пробелом), `formatGigabytes` (два знака: «2,59 ГБ»), `downloadPercent` (вниз, 0…100, `null` при неизвестном или нулевом размере).

### Мост — `src/lib/model-downloader.ts`
По образцу `task-notifier.ts`: `registerPlugin('ModelDownloader')`, `isModelDownloaderAvailable()` = `Capacitor.isNativePlatform()`. `startModelDownload(model, url)`, `readModelState(model)` — `null` в браузере; `cancelModelDownload()`, `removeModel(model)` — в браузере ничего не делают. `parseModelState(raw)` проверяет ответ целиком: `absent` / `downloading { downloaded, total | null, paused | null }` / `downloaded { size }` / `error { reason }`; неверный ответ — `error` с его текстом, чтобы экран не показал неправду.

### Нативная часть — `android/app/src/main/java/io/github/greatermagistr007/secretar/`
- `ModelDownloadState` — чистая логика, JUnit-тесты `ModelDownloadStateTest` (прогоняются задачей `test` сборки APK): состояние по записи DownloadManager (`PENDING`/`RUNNING` — качается; `PAUSED` — качается с причиной; `SUCCESSFUL` — скачана только при размере файла, равном ожидаемому, иначе ошибка; `FAILED` — ошибка с текстом по коду HTTP или `ERROR_*`), тексты причин, `isSafeFileName` (плагин удаляет файл по имени — без `/`, `\`, `\0`, `.`, `..`). Константы DownloadManager — константы времени компиляции, javac подставляет их, поэтому тесту эмулятор не нужен. Код `400` DownloadManager ставит и сам, без обращения к серверу, — так он отказывает в HTTP без шифрования; текст причины говорит об обоих вариантах.
- `ModelDownloaderPlugin` — плагин Capacitor `ModelDownloader`, зарегистрирован в `MainActivity` рядом с `TaskNotifierPlugin`:
  - `start({ url, fileName, size, title })` — отменяет прежнюю загрузку, удаляет прежний файл (DownloadManager не перезаписывает, а качает рядом под именем «…-1»), ставит `DownloadManager.Request` с `setDestinationInExternalFilesDir(..., "models", fileName)` и уведомлением о ходе загрузки, запоминает id и снимает отметку `verified_file`; адрес не http/https — отказ;
  - `status({ fileName, size })` — по запомненной загрузке, а без неё по файлу. Завершившаяся загрузка забывается: успешная с верным размером — файл отмечается `verified_file`, загрузка только забывается (`DownloadManager.remove` удалил бы и готовый файл); ошибка и неверный размер — `remove(id)` вместе с файлом; ошибка отдаётся веб-части один раз. Записи нет (отменили в системных «Загрузках», очистили данные «Диспетчера загрузок») — забыть. Без загрузки скачанной считается только файл ожидаемой длины с отметкой `verified_file`; любой другой файл удаляется как мусор: DownloadManager выделяет файл сразу полного размера, и по длине недокачанный не отличить от готового;
  - `cancel()` — `DownloadManager.remove(id)`: удаляет и недокачанный файл. Если загрузка уже завершилась успешно (нажали «Отменить» в последнюю секунду, до опроса), ничего не делает: файл остаётся, загрузку разберёт следующий `status`;
  - `remove({ fileName })` — отменяет загрузку этого файла, удаляет файл, снимает отметку `verified_file`.
  Размер читается `getData().optLong`, а не `getLong`: `PluginCall.getLong` Capacitor отдаёт `null` для числа, уместившегося в int.
- HTTP без шифрования: `android:usesCleartextTraffic="true"` в манифесте, см. [mechanic_android.md](mechanic_android.md), «HTTP без шифрования».

### Раздача модели с компьютера — `docker-compose.yml`
Команды и как узнать адрес — [deployment.md](deployment.md), раздел «Модель для голоса: раздача в локальной сети».
- `model-download` (`alpine:3.22`, от пользователя хоста): качает `https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm/resolve/<ревизия>/gemma-4-E2B-it.litertlm` в `models/<файл>.part` (`wget -c` — оборванная загрузка продолжается), проверяет SHA-256 и только потом переименовывает. Ревизия закреплена — commit `2e12bfd869b2962984f97a1f2a26807316d534cc` (поле `sha` API Hugging Face, 2026-11-20); SHA-256 `181938105e0eefd105961417e8da75903eacda102c4fce9ce90f50b97139a63c` (`lfs.oid` файла на этой ревизии). Файл с верной суммой повторно не качается; готовый файл с неверной суммой (порча на диске) удаляется перед загрузкой — иначе уже запущенный `model-server` раздавал бы его до конца перекачки. Полный `.part` с неверной суммой удаляется (иначе `wget -c` получал бы 416 и застревал).
- `model-server` (`nginx:1.30.6-alpine`): `./models` только на чтение, порт `${MODEL_PORT:-8088}`; отдаёт `Content-Length`, `ETag` и `Range` (206) — без `ETag` и `Range` DownloadManager не продолжил бы загрузку после обрыва. Ждёт успешного `model-download`.
- `models/` в `.gitignore` (`models/*`, кроме `models/.gitkeep`): каталог должен быть в клоне, иначе docker создаёт его от root и `model-download` не может писать.

## Голосовая кнопка
Решения Р-34 (голос только в APK, офлайн, звук сразу в модель, удержание кнопки) и Р-37 (сразу рабочая кнопка, полный журнал). Реализована 2026-11-21, журнал агента — `memory/progress_voice_button.md`.

### Кнопка
- `src/lib/components/VoiceButton.svelte`, вставлена в `CalendarScreen.svelte` рядом с «+»: `position: fixed`, по центру нижнего ряда (`left: 50%`), та же высота и размер 56×56, что у «+» справа. Значок микрофона — встроенный SVG, `stroke` цветом текста кнопки, толщина 2, как у «+» и стрелок проекта.
- Видна только в Android-приложении: `isVoiceAvailable()` = `Capacitor.isNativePlatform()`, как у докачки и уведомления.
- Удерживать, пока говоришь: `pointerdown` — начало (с `setPointerCapture`: уход пальца за край кнопку не отпускает), `pointerup` и `pointercancel` — отпускание; с клавиатуры — Space или Enter (нажатие — начало, отпускание — конец). После отпускания запись идёт ещё 300 мс (хвост, ход нажатия п. 4). Сворачивание приложения во время записи (`visibilitychange` → `hidden`) — тоже отпускание, но без хвоста: в фоне микрофон отдаёт тишину.
- **Совет пользователю — называть время полностью**: «в семь утра», «в 7 часов», «в три часа дня», а не короткое «в семь» или «в три». Причина: короткое «в семь» модель на слух распознаёт как «всем» («Завтра всем к стоматологу» — задача без времени), «в три» — как «с три»; опыт с 10 формулировками промпта на 19 записях владельца не дал варианта без регрессий, поэтому промпт не меняется (`memory/findings_voice_time_hearing.md`, решение владельца 2026-11-22 «Короткое время» в плане этапа 5).
- Одно нажатие за раз на всё приложение: флаг `pressing` в `<script module>` компонента. Кнопка размонтируется при уходе с календаря, а начатое нажатие продолжает обработку; без общего флага новый экземпляр пустил бы второе нажатие параллельно, и ротация журнала первого удалила бы WAV второго (ревью, Г-2). Долгое нажатие в WebView не выделяет и не открывает меню: `user-select: none`, `-webkit-touch-callout: none`, `touch-action: none`, `contextmenu` → `preventDefault`.
- Вид по состоянию (кроме значка — `aria-label` и `title`):
  - модель готова — основной цвет кнопки, микрофон;
  - модель загружается — вторичный цвет и бегущее пунктирное кольцо (`--color-primary`); нажимать можно — обработка дождётся загрузки;
  - модель не скачана или не загрузилась — вторичный цвет без кольца; нажатие объясняет причину;
  - идёт запись — заливка `--color-weekend` (цвет ошибок проекта как «красная точка записи»), кнопка чуть больше, пульсирующее кольцо;
  - подготовка и обработка — вращающаяся дуга вместо микрофона; обработка показывается сразу после отпускания, уже во время хвоста записи: палец отпущен — пользователь видит, что запись принята;
  - `prefers-reduced-motion` — без анимаций.
- Сигнал «говорите» — после фактического старта записи: плагин отвечает, когда `AudioRecord` отдал первый буфер, и в тот же момент вибрирует 40 мс; кнопка переходит в вид записи.
- Модель загружается при появлении экрана календаря (он же стартовый): `loadVoiceEngine(модель, устройство, базовый промпт дня)` вызывается при монтировании кнопки и раз в секунду, пока состояние `loading`. Повторный вызов загрузку не перезапускает. Тот же вызов — при возвращении в приложение (`visibilitychange` → `visible`) и по таймеру к ближайшей смене дня промпта (`nextPromptDayChange` + 1 с): если базовый промпт изменился, плагин перечитывает его в фоне (раздел «Базовый промпт и копия разговора»).

### Ход нажатия
1. `loadVoiceEngine(модель, устройство, базовый промпт на момент нажатия)` — состояние модели; базовый промпт другого дня плагин начинает перечитывать сразу, пока идёт запись. `absent` → ошибка «Модель не скачана: Настройки → Голос». Состояния `error` нажатие не видит: `load()` после неудачной загрузки сразу запускает её заново и отвечает `loading` — нажатие записывается и ждёт загрузку в очереди фонового потока (ожидание — `reply.waitMs`); если загрузка снова не удалась — «Ошибка голосовой команды: Модель не загружена: <класс и текст ошибки>», стек — в записи журнала `kind: "engine"`.
2. `ensureMicrophone()` — разрешение `RECORD_AUDIO` механизмом Capacitor (`@CapacitorPlugin(permissions = …, alias = "microphone")`): есть — дальше; нет — системный диалог. Выдано только что — сообщение «Микрофон разрешён. Удерживайте кнопку и говорите», запись не начинается (палец уже отпущен на диалоге). Отказ — ошибка «Нет доступа к микрофону: разрешите его в настройках телефона». Повторно спрашивается, только если разрешения нет; при «Больше не спрашивать» Android отказывает без диалога — то же сообщение.
3. `startRecording()` → вид записи и вибрация.
4. Отпускание или 30 с (`MAX_RECORD_MS`: дольше модель звук не принимает; плагин и сам обрезает запись на 30 с — `MAX_RECORD_BYTES` в `VoicePlugin.readLoop`) → кнопка в виде «обработка» → хвост записи → `stopRecording()` → WAV-файл. **Хвост** (с `versionCode` 11, решение владельца 2026-11-22 «Короткое время»): после обычного отпускания (`pointerup`, `pointercancel`, отпускание клавиши) запись продолжается `recordTailMs(holdMs)` мс — `RECORD_TAIL_MS` 300, чтобы не обрезался конец последнего слова (журнал владельца: «Завтра обед в три» — речь до последнего отсчёта записи, модель слышала «Завтра обед»). Без хвоста:
   - слишком короткое удержание (`holdMs` < `MIN_PRESS_MS`): порог п. 5 проверяется по длительности записи, и хвост не должен его перекрывать (нажатие 300 мс + хвост 300 мс прошло бы порог 500 мс); без хвоста длительность записи по-прежнему ≈ удержанию, `recordingProblem` не менялся; при удержании от 0,5 с запись с хвостом от 0,8 с — порог проходится, как и без хвоста;
   - сворачивание приложения (`visibilitychange` → `hidden`) — остановка сразу: в фоне микрофон отдаёт тишину; повторное отпускание после сворачивания (`pointercancel`) решение не меняет — флаг ставится, только пока палец на кнопке;
   - предел 30 с: по таймеру `waitRelease` хвоста нет, а у самого предела `recordTailMs` урезает хвост до `MAX_RECORD_MS − holdMs` (удержание 29,9 с — хвост 100 мс).
   Повторное нажатие во время хвоста отсекается так же, как во время обработки (флаг модуля `pressing`). Сворачивание уже во время хвоста его не обрывает — в конце записи до 300 мс тишины.
5. Запись проверяет `recordingProblem(длительность, пик)`: короче 0,5 с (`MIN_PRESS_MS`) — «Слишком короткое нажатие: удерживайте кнопку, пока говорите»; пиковый уровень ниже 300 из 32767 (`MIN_PEAK`, около −40 дБFS) — «Не слышно речи: говорите ближе к телефону». В обоих случаях модель не вызывается, WAV сохраняется, в журнале — `recording.peak` и `thresholds`. Порог тишины введён по ревью скептика (Г-1): на тишине модель выдумывала задачу; речь у телефона даёт пик в тысячи, порог уточняется по журналу владельца.
6. Обработка: `buildBasePrompt(момент нажатия, часовой пояс телефона)` (базовый промпт дня), `USER_TEXT` (сообщение нажатия), `ADD_TASK_TOOL` и путь к WAV → `runModel` (плагин, фоновый поток).
7. `interpretReply`: первый вызов `add_task` → проверка аргументов → сверка `chrono-node` → выбор даты (`chooseDate`, решение Р-39) → задача. Одна фраза — одна задача (решение владельца 2026-11-22: несколько задач из фразы отменены): если модель вызвала инструмент несколько раз, сохраняется первый вызов, остальные — только в журнале (`reply.messages`). Нет вызова — ошибка «Не понял: «<ответ модели, до 80 символов>»» (пустой ответ — «Не понял: модель ничего не ответила»; вызван не тот инструмент — «Не понял: модель вызвала неизвестный инструмент …»). Неверные аргументы — ошибка с причиной («Модель вернула неверную дату: «…»», «… неверное время …», «… пустой текст задачи»).
8. Сохранение — `onCreate` = `createTask` экрана календаря, тот же путь, что у формы: запись в хранилище, пересчёт уведомления о задачах дня (Т-31), выбор дня задачи, перечитывание сетки и списка дня.
9. Сообщение `success`: «Добавлено: Маникюр в 12 — пн, 23 ноября» (`successMessage`, день — `formatWeekdayDate` из `src/lib/date.ts`; год дописывается, только если не текущий).
10. Любая ошибка — всплывающее `error` с текстом; непредвиденная — «Ошибка голосовой команды: <текст>». Запись, прерванная ошибкой, останавливается, микрофон освобождается.
11. Всегда, чем бы ни кончилось, — запись нажатия в журнал.

### Плагин Voice — `android/.../VoicePlugin.java`
Зарегистрирован в `MainActivity`; мост — `src/lib/voice.ts`. Системный промпт и описание инструмента плагин получает от веб-части, сам их не собирает.
- `load({ fileName, size, device, systemPrompt?, tool? })` — если файл `getExternalFilesDir("models")/<файл>` той же длины и отмечен загрузчиком проверенным (`model_downloader.xml`, `verified_file`), запускает загрузку в фоновом потоке на устройстве `device` (`GPU` или `CPU`, иное — отказ) и сразу отвечает состоянием `{ state: absent | loading | ready | error, backend, mtp, loadMs, error }`. Модель удалили или заменили — движок закрывается, состояние `absent`. Другое устройство, чем у текущей загрузки, — перезагрузка; результат прежней загрузки отбрасывается по номеру загрузки (`loadGeneration`). `systemPrompt` и `tool` — базовый промпт дня (запоминается как нужный); модель готова, а прочитан другой — перечитывание в фоне.
- Загрузка (с 2026-11-22, APK `versionCode` 8): попытки по очереди — выбранное устройство с MTP-драфтером, оно же без MTP, затем (если выбран GPU) CPU с MTP и CPU без MTP: `Engine(EngineConfig(путь, backend, visionBackend = null, audioBackend = CPU, maxNumTokens = 2048, maxNumImages = null, cacheDir = cacheDir приложения, activationDataType = null, speculativeDecodingConfig = SpeculativeDecodingConfig(ON | OFF)))`, затем прогрев — разговор без инструментов, текст «Привет», `maxOutputToken = 8` (несколько токенов, а не один — чтобы драфтер отработал шаг и его отказ случился при загрузке, а не на первом нажатии). Ошибка загрузки или прогрева — движок закрывается, следующая попытка; ошибки всех попыток — в запись журнала о загрузке. После загрузки — чтение базового промпта, если он уже известен.
- **MTP** (speculative decoding, драфтер `tf_lite_mtp_drafter` уже внутри файла модели): по умолчанию в LiteRT-LM 0.19.1 выключен (`Config.kt` тега v0.19.1, стр. 201–206: «Fields left null use the runtime defaults (mode OFF). ON and ADAPTIVE load the drafter when the engine is initialized»). Режим ON: на CPU компьютера ответ ×1,65–2,5 быстрее при тех же ответах (`memory/findings_voice_speed_host.md`, п. 9), по Google на мобильных GPU до ×2,2. Статистики драфтера (доли принятых токенов) в API 0.19.1 нет: `BenchmarkInfo` её не содержит, библиотека пишет её только в свой лог при уничтожении драфтера (`runtime/executor/llm_litert_mtp_drafter.cc`, стр. 206–213); эффект MTP виден в журнале по `decodeTokensPerSecond`. На эмуляторе без OpenCL GPU с MTP отказывает уже при создании движка («Can not find OpenCL library on this device»), GPU без MTP — на прогреве.
- **Окно контекста `maxNumTokens` 2048** (было 4096): модель компилируется под размер KV-кэша, и на CPU компьютера 2048 вместо 4096 ускоряет чтение на 22 % и генерацию в 1,4 раза при тех же ответах (`memory/findings_voice_speed_host.md`, п. 10; 1280 не работает вовсе). Расчёт по токенам: базовый промпт 1051–1053 днём и 1118 ночью (эмулятор), звук 25 ток/с — 30 с записи = 750, сообщение нажатия с разметкой ≈ 15–20, ответ — до 128: 1118 + 750 + 20 + 128 = 2016 < 2048, запас около 30 токенов (раздел «Известные границы кнопки»). Зачем прогрев: на эмуляторе без OpenCL `initialize()` на GPU прошёл (LiteRT взял WebGPU), а первый же запрос упал с `Can not find OpenCL library on this device` — без прогрева это случилось бы на первом нажатии пользователя; заодно первое нажатие не ждёт компиляции ядер. Неудавшийся GPU-движок закрывается в отдельном потоке: на эмуляторе его закрытие висело в `vkQueueWaitIdle` драйвера Vulkan около полутора минут, и загрузка на CPU ждала бы его. Аудиоэнкодер в файле модели жёстко на CPU (находка скептика С-4). Зрение не включается (`visionBackend = null`). `cacheDir` ускоряет вторую загрузку. Движок держится в статических полях, пока жив процесс; загрузка и инференс идут по очереди в одном фоновом потоке — нажатие во время загрузки ждёт её конца.
- `startRecording()` — `AudioRecord` (`MIC`, 16 кГц, моно, PCM16, буфер не меньше 0,1 с), отвечает после первого прочитанного буфера (не дольше 1 с ожидания): `{ startMs, firstBuffer, bufferBytes, source }`; вибрация 40 мс. Нет разрешения — отказ с кодом `permission`.
- `stopRecording()` — останавливает, пишет `voice-<ггггММдд-ЧЧммсс-SSS>.wav` в каталог журнала, отвечает `{ file, path, sampleRate, channels, bitsPerSample, bytes, samples, durationMs, recordedMs, peak, truncated }`. `peak` — наибольший модуль отсчёта 0…32768: около нуля — микрофон отдал тишину.
- `process({ audioPath, systemPrompt, userText, tool })` — `systemPrompt` — базовый промпт дня, `userText` — сообщение нажатия. Разговор нажатия — копия базового (`clone()`), если прочитана база того же текста; иначе — новый разговор с промптом нажатия, одно чтение, как до 2026-11-22 (`mode: fresh`, `freshReason`: «база другого текста» — нажатие на границе дня, «база не прочитана», «копия не удалась» с `cloneError`). Базу под нажатие плагин не перечитывает (ревью У-3): её перечитывает `load()`, вызванный в начале того же нажатия, — он стоит в очереди раньше `process`. Если сменили устройство, пока нажатие ждало в очереди, оно доделывается на прежнем движке: его закроет только загрузка, стоящая в очереди после нажатия (ревью У-11); в журнале тогда `config.device` — новое устройство, `config.backend` — прежнее. Настройки разговора (база и новый): `ConversationConfig(systemInstruction = промпт, tools = [ToolKt.tool(OpenApiTool с описанием tool)], samplerConfig = SamplerConfig(topK 1, topP 1.0, temperature 0.0, seed 0), automaticToolCalling = false, prefillPrefaceOnInit = true, maxOutputToken = 128, thinkingConfig = ThinkingConfig(false, -1))`; сообщение пользователя — `Content.AudioFile(путь)` и текст `userText`. Ответ: `{ messages: [{ role, text, toolCalls: [{ name, arguments }], channels }], backend, waitMs, conversationMs, inferenceMs, conversation, config, timing }` (раздел «Журнал»).
- **Базовый промпт и копия разговора** (с 2026-11-22, APK `versionCode` 8): постоянная часть промпта — всё, что зависит только от дня (правила, «сегодня/завтра/послезавтра», календарь, ночное правило), и описание инструмента — читается моделью один раз в базовый разговор (`prefillPrefaceOnInit = true`): после загрузки модели и при смене текста. На нажатие — `clone()` (копия истории и KV-кэша, `Conversation.kt` тега v0.19.1, стр. 738–753; `conversation.cc` стр. 993–1020 → `SessionAdvanced::Clone` в `session_advanced.cc` стр. 436–473) и сообщение нажатия (`USER_TEXT`) со звуком. Ход клона рендерится разностью шаблонов (`conversation.cc`, стр. 319) — модель видит ту же последовательность токенов, что у нового разговора с тем же промптом. Плагин сравнивает текст базы и инструмента целиком (`baseIsWanted`), веб-часть — ключ дня (`promptDayKey`): перечитывание — в фоне при запуске, возвращении в приложение и по таймеру к 00:00 и 04:00; если к нажатию текст другой — его ставит в очередь `load()` самого нажатия, раньше `process`, пока идёт запись (на эмуляторе: время видно в `reply.waitMs`, а `conversation.base.at` — момент нажатия). Неудачное чтение базы не повторяется на каждом нажатии: текст запоминается как прочитанный с ошибкой (`conversation.base.error`), повтор — при смене текста или перезагрузке модели (ревью У-4). Копия на CPU эмулятора — 0–1 мс. Базовый разговор закрывается раньше движка (`closeEngine`) и при перечитывании.
- Замеры движка включены (`ExperimentalFlags.enableBenchmark = true` до создания `Engine`). В LiteRT-LM 0.19.1 с нулевыми параметрами бенчмарка вход не подменяется (`runtime/core/session_utils.cc:66-78`, `session_advanced.cc:73,119` — подмена только при `num_prefill_tokens > 0`) и декод останавливается по стоп-токенам (`tasks.cc:96-107`); цена — prefill ждёт своего завершения (`tasks.cc:613-614`), декоду он всё равно нужен готовым.
- `writeLog({ line })`, `logInfo()`, `clearLog()`, `shareLog()` — журнал, раздел «Журнал».
- Чистая логика вынесена в `WavFile` (заголовок WAV 44 байта, пик, длительность), `VoiceLog` (ротация) и `ModelTiming` (сводка времени ответа модели, с 2026-11-22; с `versionCode` 8 — с ходами ответа инструмента) — JUnit `WavFileTest`, `VoiceLogTest`, `ModelTimingTest`.

### Инструмент add_task — штатный механизм LiteRT-LM 0.19.1
- Описание — `OpenApiTool` (интерфейс Java: `getToolDescriptionJsonString()`, `execute()`), регистрация — `ToolKt.tool(OpenApiTool)` (проверено `javap` по AAR 0.19.1).
- **Ручной режим**: `automaticToolCalling = false`. При вызове инструмента `Conversation.sendMessage` сразу возвращает сообщение с `toolCalls` (`Conversation.kt` тега v0.19.1: `if (!automaticToolCalling) return jsonToMessage(...)`), `execute()` не вызывается (раздел «Manual Tool Calling» в `docs/api/kotlin/getting_started.md` того же тега), догенерации после вызова нет. Аргументы веб-часть берёт из ответа.
- **Одна фраза — одна задача** (решение владельца 2026-11-22; в APK 8 были несколько задач ходами с ответом инструмента — отменены в APK 9: ход «Готово» на GPU телефона стоил около 2 с). Библиотека разбирает все блоки вызовов в ответе (`runtime/components/tool_use/parser_utils.cc` v0.19.1, стр. 229–276), но Gemma 4 после первого `<tool_call|>` сама выдаёт стоп-токен — ждёт ответа инструмента (сырой вывод Session API на компьютере), так что ответ — один вызов; если вызовов всё же несколько, сохраняется первый, остальные — в журнале.
- Принудительного вызова (`ToolChoice`) в 0.19.1 нет (находка скептика С-1) — модель решает сама, вызывать ли инструмент; не вызвала — «Не понял» и ответ модели в журнале. Это и есть выбор владельца «модель сама вызывает tool call».

### Системный промпт: база дня и сообщение нажатия
Собирается в веб-части — `src/lib/voice-command.ts`: там же описание инструмента и разбор ответа, всё покрыто тестами, а дата, день недели и часовой пояс (`Intl.DateTimeFormat().resolvedOptions().timeZone`) берутся там же, где работает остальное приложение. С 2026-11-22 (APK `versionCode` 8) промпт разделён на две функции:
- `buildBasePrompt(момент, часовой пояс)` — базовый промпт: всё, что зависит только от дня; плагин читает его один раз и копирует разговор на нажатие (раздел «Базовый промпт и копия разговора»). Времени суток в нём нет.
- `USER_TEXT` — сообщение нажатия к записи: «Команда пользователя — в аудиозаписи.». Времени нажатия в нём нет (APK 9, ревью У-2): в APK 8 было «Сейчас ЧЧ:ММ. …», и модель брала это время в `time` («Сегодня забрать Азон» → 15:01, «Сегодня в пять забрать машину» → 15:04, журнал телефона 22.11 15:01–15:04); ни одно правило промпта от времени суток не зависит.
- `promptDayKey(момент)` — ключ дня промпта «ГГГГ-ММ-ДД день|ночь»: база зависит только от него и часового пояса, меняется на границах 00:00 и 04:00 (`NIGHT_END_HOUR`); в журнал — `request.baseKey`. `nextPromptDayChange(момент)` — ближайшая смена ключа (04:00 ночью, иначе полночь), к ней — таймер кнопки.
Календарь на 15 дней снимает с модели арифметику дней недели.
Правило дня недели: «в понедельник» — ближайший понедельник **после** сегодняшнего; если сегодня понедельник — через 7 дней (план этапа 5, «следующий ближайший»; дата и день недели всегда видны в сообщении об успехе).
Время: «в 12» — 12:00, «в 7 вечера» — 19:00; без «утра/дня/вечера» — как сказано («в 7» — 07:00). Время не названо — `time` не передаётся.
**Ночное правило** (решение Р-38, уточнено владельцем 2026-11-22): до 04:00 (`NIGHT_END_HOUR`) календарного дня D «сегодня», «завтра» и день без названия — D, «послезавтра» — D+1, дни недели — от D−1 (ближайший такой день не раньше D: в ночь на воскресенье «в воскресенье» — это воскресенье D, «в субботу» — через 6 дней), прошедший день не получается никогда. Календарь ночью начинается с D, метки — «сегодня и завтра», «послезавтра». «Через N дней» ночью — от D (так считает модель; владелец решил не добиваться иного). С 04:00 — обычное правило. Сверка `chrono-node` ночью идёт от прошлых суток (`dayReference`), а дата прошлых суток приводится к D.
Проверка на компьютере (`memory/progress_voice_speedup.md`, разделы «Проверка качества на хосте» и «APK 9: исправления по ревью»): 12 записей владельца (журналы телефона 22.11 01:58–15:04), окно 2048, один ход. APK 9 против APK 8 на телефоне: утечки времени нажатия нет («Сегодня забрать Азон» — без времени, было 15:01; «третьего декабря у обед…» — без времени, было 15:00); даты остальных фраз — те же; ночью «двадцать первого декабря» — 21.12 (промпт APK 7 давал 05.12). Отличия текста: «Корпоративный» вместо «Корпоратив», «вайlbерис» (написание плавает и на старых промптах). MTP ON и OFF дают одинаковые ответы на всех 12 записях и 12 текстовых фразах.

### Разбор ответа и сверка дат — `src/lib/voice-command.ts`
- `parseAddTaskArgs`: аргументы — объект; `date` — существующая дата `ГГГГ-ММ-ДД` (`isIsoDate`); `time` — `Ч:ММ` или `ЧЧ:ММ` в пределах суток, приводится к `ЧЧ:ММ`, пусто или `null` — без времени; `text` — обрезается, точка в конце убирается, первая буква заглавная, пустой — ошибка; `heard` — строка или отсутствует.
- `taskText`: время в тексте задачи (выбор 6.1): «Маникюр в 12», при ненулевых минутах «Маникюр в 12:30», часы без ведущего нуля. Приоритет — средний, без повторения (у голосовой команды их пока нет).
- `checkDateWithChrono` (выбор 5.2): `chrono-node/ru`, `forwardDate`, по `heard`. Сверяется только дата и только если в фразе назван день (`isCertain('day')` или `isCertain('weekday')`): «маникюр в 12» `chrono-node` относит к ближайшим 12:00 — это может быть завтра. День недели, выпавший у `chrono-node` на сегодня, сдвигается на 7 дней — так правило совпадает с промптом (сам `chrono-node` 2.10.3 в понедельник утром даёт «в понедельник» = сегодня, вечером — через неделю, проверено). Итог `{ found, matched, date, agrees }`; что делать с расхождением — решает `chooseDate` (ниже). Ночью (до 04:00, с 2026-11-22) разбор идёт от того же времени прошлых суток (`dayReference`) — так «завтра» и дни недели совпадают с промптом, — а дата прошлых суток («сегодня», «21 ноября» в ночь на 22-е) приводится к календарной: прошедшего дня промпт не даёт. Ночью бывают ложные расхождения (только в журнале, ревью У-6): «через два дня» — `chrono-node` считает от D−1 (23-е), модель от D (24-е); «через неделю» — 28-е против 29-го; явно названное «21 ноября» в ночь на 22-е `chrono-node` приводит к 22-му, а модель по правилу «не раньше сегодняшней» даёт 2027-11-21.
- `chooseDate` (решение Р-39 — дата голосовой задачи: «сегодня», «завтра», «послезавтра» — по `chrono-node`; с APK `versionCode` 10): если `chrono-node` распознал в `heard` «сегодня», «завтра» или «послезавтра» и его дата (с ночным правилом, как в сверке) расходится с датой модели — задача и сообщение об успехе — по дате `chrono-node`; иначе — по дате модели, расхождение только в журнале. Слово ищется в распознанном куске `chrono.matched` (первый результат `chrono-node`) регуляркой `RELATIVE_DAY`: отдельное слово без учёта регистра, границы — «не кириллическая буква» (`\b` в JS кириллицу не понимает); тегам не доверяем — у «послезавтра» в `chrono-node` 2.10.3 их нет. «Послезавтра» и «завтра» не путаются: дата берётся у `chrono-node`, а он их различает. Учитывается только первый распознанный кусок: «в понедельник маникюр, а завтра хлеб» → день недели, дата модели. Итог `{ model, chrono, saved, source }`: дата модели, дата `chrono-node` (null — день не назван), сохранённая дата, источник `model` или `chrono`. Пример из журнала телефона: «Сегодня в пять забрать машину», модель → 2026-11-27, нажатие 22.11 15:04 → сохраняется 2026-11-22. Ночью (до 04:00 22.11): «завтра в 12» → 22.11, «сегодня» → 22.11, «послезавтра» → 23.11.
- `interpretReply(сообщения, момент)` → `{ ok: true, args, chrono, dateChoice, task, toast }` или `{ ok: false, error, rawArgs }` (первый вызов `add_task`).

### Журнал
- Где: `getExternalFilesDir("voice-logs")` = `/sdcard/Android/data/io.github.greatermagistr007.secretar/files/voice-logs/`: `voice-log.jsonl` и WAV-файлы нажатий. Каталог исключён из резервной копии (`backup_rules.xml`, `data_extraction_rules.xml`), удаляется вместе с приложением.
- Формат — JSON Lines, одна строка на событие, кириллица без экранирования. Запись нажатия (`kind: "press"`, первым полем — по нему считаются нажатия) пишет веб-часть:
  - `at` — момент нажатия, локальное время со смещением (`2026-11-21T19:30:05.123+03:00`), `timeZone`, `model` — файл модели, `thresholds` — `minPressMs` и `minPeak`, по которым проверялась запись, с `versionCode` 11 — `recordTailMs` (хвост записи после отпускания, 300);
  - `steps` — мс по шагам: `engineMs`, `permissionMs`, `recordStartMs` (нажатие → фактический старт записи), `holdMs`, `tailMs` (с `versionCode` 11 — фактическое ожидание хвоста: около 300, 0 у короткого нажатия, сворачивания и предела 30 с), `recordStopMs`, `modelMs` (весь вызов модели), `interpretMs`, `saveMs`, `totalMs`; шаги, до которых не дошло, отсутствуют;
  - `engine` — состояние модели на момент нажатия (устройство GPU/CPU, время загрузки); `permission`;
  - `recordingStart`, `recording` — параметры и итог записи (частота, отсчёты, длительность, пик, обрезка, имя WAV);
  - `device` — выбранное устройство для модели (с `versionCode` 8);
  - `request` — всё, что отдано модели: путь к WAV, `systemPrompt` — базовый промпт дня целиком, `userText` — сообщение нажатия, описание инструмента, `baseKey` — ключ дня промпта;
  - `reply` — ответ плагина как пришёл: все сообщения (текст, вызовы с аргументами, каналы), `backend`, `waitMs` (ожидание очереди, например догрузки модели), `conversationMs` (подготовка разговора нажатия: копия базы, а если база перечитывалась перед нажатием или копия не удалась — вместе с чтением промпта), `inferenceMs` (звук, ход пользователя, ответ), `conversation` — как подготовлен разговор (с `versionCode` 8): `mode` (`clone` — копия базы, `fresh` — новый разговор), `cloneMs`, `cloneError` (стек, если копия не удалась), `freshReason` (почему новый разговор), `base` — база на момент нажатия: `reason` («после загрузки модели», «сменился текст (проверка модели)»), `at` — когда прочитана, `prefillMs`, `preface` (замеры чтения: токены, ток/с) или `error` и `failedAfterMs`; `config` (сэмплер, `maxNumTokens`, `maxOutputTokens`, размышление, ручной режим, устройство звука, с `versionCode` 8 — `device` выбранное, `backend` фактическое, `mtp` — ON или OFF), `timing` — разбивка времени (с 2026-11-22, Р-38), из `Conversation.getBenchmarkInfo()`:
    - `conversationMs` — подготовка разговора (см. выше); `preface` — только у нового разговора (`mode: fresh`): замеры после его создания — `prefillTokens` (токенов в промпте с описанием инструмента), `prefillTokensPerSecond`, `prefillMs`; у копии чтение базы — в `conversation.base.preface`;
    - `turn` — замеры после ответа: `prefillTokens` (ход пользователя: звук, текст и разметка шаблона одним списком — отдельного числа токенов звука библиотека не отдаёт; у Gemma 4 около 25 токенов на секунду звука), `prefillTokensPerSecond`, `prefillMs`, `decodeTokens`, `decodeTokensPerSecond`, `decodeMs`, `marksMs.audio_executor` — аудиоэнкодер (CPU), `timeToFirstTokenMs` — TTFT по определению библиотеки (первый ход prefill, то есть промпт, плюс средний токен декода, `io_types.cc:357-367`);
    - сводка (класс `ModelTiming`, JUnit `ModelTimingTest`): `audioEncodeMs`, `turnPrefillMs`, `decodeMs`; `firstTokenMs` — до первого токена ответа от начала работы модели над нажатием: подготовка разговора (`conversationMs`: у копии 0–1 мс, чтение промпта — только у нового разговора) + звук + prefill хода + один токен декода (расчёт по замерам; без ожидания очереди `waitMs` и записи WAV; ответ — вызов инструмента, потокового первого токена у него нет); `modelTotalMs` — ответ модели целиком, `conversationMs + inferenceMs`; `otherMs` — остаток `inferenceMs`: чтение WAV и спектрограмма, рендер шаблона и токенизация хода, разбор ответа, вызовы JNI и замер промпта между созданием разговора и `sendMessage`; всего токенов в разговоре — промпт (`conversation.base.preface.prefillTokens` у копии, `preface.prefillTokens` у нового) + `turn.prefillTokens` + `turn.decodeTokens`;
    - замер не удался — вместо чисел `error` с текстом, нажатие не прерывается; при ошибке модели собранные замеры (`conversationMs`, `preface`) — в `error.data.timing`;
    - `initTimeInSecond` библиотеки в журнал не берётся: JNI (`litertlm.cc:191-196`) суммирует все фазы инициализации, и «Init Total» входит вместе со своими частями, плюс фазы сессии и разговора (с чтением промпта) — число получается примерно вдвое больше загрузки;

### Известные границы кнопки
- **Ночью «через N дней» считается от текущего календарного дня D** (так считает модель, решение владельца 2026-11-22 — не добиваться иного): в 03:00 22 ноября «через два дня» — 24 ноября.
- **Одна фраза — одна задача**: «во вторник и в среду …» сохраняется только на вторник (решение владельца 2026-11-22).
- **«Сегодня в пять забрать машину» (звук) → 27 ноября, пятница** — и на телефоне (APK 8), и на компьютере с промптами APK 7, APK 8 и APK 9, с MTP и без: модель путает «в пять» с «в пятницу»; на текстовой фразе — верно. С APK `versionCode` 10 задача сохраняется по дате `chrono-node` (сегодня), если в `heard` есть «Сегодня» (решение Р-39, `dateChoice`). «В четыре забрать машину» без дня → завтрашний день (на всех промптах). Видно по `chrono` (день не назван — сверки нет) и `args`.
- **Текст вместо вызова** («<|tool_call>callLaptop», телефон, APK 8, GPU) на компьютере не воспроизводится — там та же запись даёт вызов; причина — вероятно, численные отличия GPU; «Не понял» с текстом ответа в журнале.
- **Запас окна ночью — около 30 токенов** (ревью У-5): база ночью 1118 токенов + 30 с звука 750 + сообщение около 20 + ответ до 128 ≈ 2016 из 2048; длинное имя часового пояса добавляет токены. Переполнение — ошибка модели в журнале; проверяется тест-кейсом 21.
- **Нажатие на границе дня промпта** (00:00, 04:00) может пойти новым разговором (`freshReason` «база другого текста») — одно чтение промпта, как до APK 8.
- **«Сегодня ночью» днём** (с `versionCode` 10, Р-39): `chrono-node` 2.10.3 относит «сегодня ночью» к 00:00 следующих суток (22.11 15:04 → 23.11), поэтому если модель дала 22.11, задача сохранится на 23.11 (`dateChoice.source: chrono`). «Сегодня в 3» днём `chrono-node` оставляет на сегодня (03:00), «сегодня вечером» — 20:00 того же дня. Проверено на компьютере; правилом не закрыто — по журналу владельца.
- **День недели, совпадающий с сегодняшним**: на компьютере на текстовых фразах (вместо звука) в воскресенье днём «в воскресенье» модель отдала сегодняшнее воскресенье, а не через 7 дней; в понедельник «в понедельник» — 27.11, «в воскресенье» — 06.12 (ошибалась так и на старом промпте). Расхождение с `chrono-node` видно в журнале (`chrono.agrees`). На звуке не проверялось.
- **Время «в 4» без «утра/дня/вечера»** на текстовых фразах модель не передавала (и на промпте APK 7); видно по `args.time`. Утечка времени нажатия в `time` (APK 8) устранена в APK 9 — времени в сообщении нет.
- **Тишина при нулевом пороге** (только проверочная сборка APK 8 на эмуляторе): модель взяла текст из сообщения нажатия («Сейчас 14:45» → задача «Сейчас»); в рабочей сборке порог `MIN_PEAK` 300 такие записи в модель не пускает.
- **Отказ `clone()` и отказ MTP на телефоне не воспроизводились**: откаты (новый разговор, загрузка без MTP) проверены только чтением кода; их причина попадает в журнал (`conversation.cloneError`, `gpuMtpError`/`cpuMtpError`).
- Принудительного вызова инструмента нет (С-1): модель может ответить текстом — это видно в журнале.
- Качество русской речи у Gemma 4 не измерено (план этапа 5) — меряется журналом нажатий владельца.
- Источник звука — `MIC` (с системной обработкой телефона). `VOICE_RECOGNITION` на части телефонов тише; если журнал покажет низкий пик при нормальной речи — пробовать его.
- Повторений, приоритета и других команд голосом нет: задача — средний приоритет, без повторения.
- Первое нажатие уходит на диалог разрешения — говорить нужно вторым нажатием.
- Модель грузится, пока открыт экран календаря, и держится в памяти, пока жив процесс (около 1,7–2 ГБ на CPU по карточке модели); выгрузки при сворачивании нет — система может убить процесс в фоне, тогда следующая загрузка — заново.
- **На тишине модель выдумывает задачу**: на эмуляторе (`peak` 8) модель вызвала `add_task` с `heard` «в воскресенье завтра купить молоко», и задача сохранилась, хотя промпт велит на пустой фразе инструмент не вызывать. Закрыто порогом `MIN_PEAK` (ход нажатия, п. 5). Тихая, но не пустая запись выше порога (шум комнаты) по-прежнему может дать выдумку — видно по `recording.peak` и `heard` в журнале.
- **«Сырой ответ» в журнале — сообщение после разбора библиотекой**: сырой текст модели (токены вызова) в LiteRT-LM 0.19.1 недоступен — публичный API отдаёт только `Message` после `jsonToMessage` (`Conversation.kt`), нативный слой (`LiteRtLmJni`) внутренний. В журнале — текст, вызовы и каналы; нетекстовые части ответа и вызовы без `function` библиотека отбрасывает.
- **Процесс убит во время обработки** (сворачивание при RSS около 2,7 ГБ на CPU) — записи нажатия нет: её пишет веб-часть в конце нажатия; WAV остаётся без упоминания и удаляется при следующей записи нажатия.
- **Зависание загрузки вешает кнопку**: у обработки нет таймаута, загрузка и обработка — в одном фоновом потоке; если `initialize()` или закрытие движка не вернётся, нажатие остаётся в виде «обработка» без записи в журнал до перезапуска приложения. Закрытие неудавшегося GPU-движка уже вынесено в отдельный поток (на эмуляторе оно висело около полутора минут).
- **Записи о загрузке модели теряются после 30 нажатий**: ротация оставляет всё, что после 30-го с конца нажатия; устройство при этом есть в каждом нажатии (`engine.backend`, `reply.backend`).
- **Кэш LiteRT-LM в `cacheDir` занимает около 0,9 ГБ и больше**: на эмуляторе после загрузки — `…_mldrift_weight_cache.bin` 776 629 712 байт и `…_mldrift_program_cache.bin` 13 МБ (GPU), `…static_audio_encoder.xnnpack_cache` 91 МБ, `…audio_adapter.xnnpack_cache` 9 МБ; при откате на CPU добавляется кэш текстовой части. Кэш ускоряет повторную загрузку; система вправе удалить его при нехватке места — тогда загрузка снова долгая. В «Хранилище» приложения это видно как «Кэш».

## Примечания

### Известные границы
- **DownloadManager при обрыве сам повторяет попытки** (паузы растут: 2, 2, 4 мин и дальше) и после нескольких неудач завершает загрузку ошибкой — до ошибки около 15–20 минут повторов. Пока он ждёт, экран показывает «Скачивается: …» и «Нет связи с сервером, повтор через некоторое время»; отменить можно сразу. Так же выглядит и неверный адрес, указывающий на несуществующий компьютер, — проверку адреса заранее DownloadManager не делает.
- **Сеть загрузки не ограничена Wi-Fi** (`setAllowedNetworkTypes` не задан): при переходе телефона с Wi-Fi на мобильную сеть DownloadManager попытается продолжить через неё, адрес локальной сети оттуда недостижим — экран покажет паузу «Нет связи…», после возврата в Wi-Fi загрузка продолжится (на устройстве не проверено, тест-кейс 14).
- **Файл выделяется сразу полного размера**: во время загрузки размер файла на диске уже 2 588 147 712 — по нему нельзя судить о прогрессе. Проверка размера после успеха ловит другой файл на сервере (другой `Content-Length`); обрезанную передачу DownloadManager сам завершает ошибкой.
- **Принудительная остановка приложения загрузку не прерывает** — её ведёт системный процесс загрузок.
- **«Отменить» в последнюю секунду**, когда загрузка уже завершилась, файл не удаляет: модель остаётся скачанной, экран сообщает «Gemma 4 E2B скачана».
- **Резервная копия и перенос на новый телефон** модель и состояние её загрузки не содержат — после восстановления модель скачивается заново.
- **Подтверждения перед «Удалить модель» нет**: удаление обратимо повторной докачкой (по локальной сети около полутора минут на эмуляторе).
- HTTP разрешён приложению целиком, а не только для локальной сети, — см. mechanic_android.md.
- Свободного места DownloadManager требует сам; при нехватке — ошибка «Недостаточно места на телефоне» (на эмуляторе не воспроизводилась: раздел данных расширен до 6 ГБ).

### Тест-кейсы для проверки на телефоне
1. На компьютере: `env UID=$(id -u) GID=$(id -g) docker compose up -d model-server`; узнать адрес компьютера в сети (deployment.md). Телефон и компьютер — в одной сети Wi-Fi.
2. Настройки → Голос: выбрана «Gemma 4 E2B», «Не скачана».
3. Ввести `адрес:8088` → «Скачать» → прогресс в МБ и процентах на экране и в шторке; по окончании — «Скачана, 2,59 ГБ» и сообщение «Gemma 4 E2B скачана».
4. Свернуть приложение во время скачивания и вернуться — прогресс продолжается.
5. Закрыть приложение из «недавних» во время скачивания и открыть снова — экран показывает идущую загрузку.
6. Остановить раздачу (`docker compose stop model-server`) во время скачивания → «Нет связи с сервером…»; запустить (`docker compose start model-server`) — загрузка продолжается с того же места.
7. «Отменить» во время скачивания → «Не скачана», место освобождено (Настройки телефона → Приложения → Секретарь → Хранилище).
8. «Удалить модель» → «Не скачана», место освобождено.
9. Неверный адрес (`abc:99999`, `http:/адрес`) → сообщение об ошибке без загрузки; адрес без раздачи → «Нет связи с сервером, повтор через некоторое время»; до ошибки «Нет связи с сервером: проверьте адрес и что раздача запущена» — около 15–20 минут повторов, отменить можно сразу; верный адрес с лишним путём (`адрес:8088/x`) → «На сервере нет файла модели (HTTP 404)».
10. Открыть Настройки → Голос в браузере (PWA) → пояснение, что докачка только в Android-приложении.
11. Модель скачана → поставить новый APK поверх (тот же ключ, больший `versionCode`) → «Скачана, 2,59 ГБ», файл на месте.
12. Удалить приложение и поставить снова → «Не скачана», в Настройках телефона места под модель не занято (каталог удалён вместе с приложением).

15. Нехватка места: телефон с менее чем 2,6 ГБ свободного → ошибка «Недостаточно места на телефоне», экран «Не скачана».

### Тест-кейсы голосовой кнопки на телефоне
APK `versionCode` 6, модель уже скачана (тест-кейсы выше). После каждого кейса журнал можно выгрузить и отдать на разбор.
1. Поставить APK поверх `versionCode` 5 → «Настройки → Голос»: «Скачана, 2,59 ГБ» — модель не пропала.
2. Открыть приложение → на экране календаря по центру нижнего ряда микрофон, справа «+». Несколько секунд кнопка в виде «загружается» (бегущее кольцо), затем основного цвета.
3. Первое нажатие → системный диалог «Разрешить запись аудио?» → «Разрешить» → сообщение «Микрофон разрешён. Удерживайте кнопку и говорите». Запись не начинается.
4. Удерживать кнопку → короткая вибрация, кнопка красная и пульсирует → сказать «в понедельник маникюр в 12» → отпустить → вращающаяся дуга → «Добавлено: Маникюр в 12 — пн, 23 ноября» (дата — ближайший понедельник после сегодняшнего), задача в списке понедельника, метка в сетке.
5. Фразы на проверку правил: «завтра купить хлеб» (без времени), «послезавтра в 7 вечера позвонить маме» → «… в 19», «25-го оплатить интернет», «в субботу в половине восьмого пробежка», сегодняшний день недели («в субботу …» в субботу) → через 7 дней, фраза без дня «маникюр в 12» → сегодня.
6. Нажать и сразу отпустить → «Слишком короткое нажатие: удерживайте кнопку, пока говорите». Удерживать 2–3 с молча, прикрыв микрофон, → «Не слышно речи: говорите ближе к телефону», в журнале `recording.peak` ниже 300 и нет `reply`. Сказать фразу шёпотом издалека — посмотреть по журналу, какой пик даёт речь владельца, и уточнить порог.
6а. Начать запись и свернуть приложение, не отпуская, → запись завершается при сворачивании; по возвращении — результат или ошибка, запись в журнале.
7. Сказать что-то не про задачу («как дела») → «Не понял: «…»» с ответом модели (или задача, если модель всё же вызвала инструмент — видно в журнале).
8. Держать кнопку дольше 30 с → запись сама останавливается на 30 с и уходит в модель (`recording.truncated: true` в журнале).
9. Палец увести с кнопки, не отпуская, — запись продолжается до отпускания; долгое нажатие не открывает меню и не выделяет текст.
10. Отказать в разрешении («Не разрешать») → «Нет доступа к микрофону: разрешите его в настройках телефона»; после второго отказа Android больше не спрашивает — то же сообщение; разрешить в «Настройки телефона → Приложения → Секретарь → Разрешения → Микрофон» → кнопка работает.
11. «Настройки → Голос → Удалить модель» → на календаре кнопка вторичного цвета, нажатие → «Модель не скачана: Настройки → Голос».
12. «Настройки → Голос → Журнал»: «Записей: N» совпадает с числом нажатий (не больше 30) → «Поделиться журналом» → меню «Поделиться» → Telegram → в чат уходит `secretar-voice-log-<дата>.zip` с `voice-log.jsonl` и WAV-файлами; WAV проигрывается и звучит как сказанное.
13. «Очистить журнал» → «Журнал очищен», «Записей: 0», кнопки журнала недоступны.
14. Время ответа: в журнале `engine.backend` (GPU или CPU), запись `kind: "engine"` с `loadMs`, у нажатия `steps.modelMs` и `reply.inferenceMs` — по ним видно, сколько занимает каждое нажатие на этом телефоне.
15. Свернуть приложение на минуту и вернуться → нажатие работает без повторной загрузки (`steps.engineMs` — единицы мс, записи `engine` нет); после закрытия из «недавних» — модель грузится заново (новая запись `engine`).
16. (`versionCode` 9) Сказать «во вторник и в среду надо заехать в берёзовый» → одна задача (вторник), сообщение «Добавлено: Заехать в берёзовый — вт, …»; в журнале нет `timing.rounds`. Сказать «сегодня забрать Озон» → задача без времени (не время нажатия).
17. (`versionCode` 8+) Запись `engine`: `mtp: "ON"` (или `OFF` и `gpuMtpError` со стеком — откат), `maxNumTokens: 2048`, с `versionCode` 9 — `accepted: true`; у нажатия `reply.conversation.mode: "clone"`, `cloneMs`, `conversation.base.at` — время загрузки модели, `timing.turn.decodeTokensPerSecond` против 9 ток/с в журнале №2.
18. (`versionCode` 8+) «Настройки → Голос → Процессор (CPU)» → «Модель перезагружается: Процессор (CPU)», новая запись `engine` с `device: "CPU"` в пределах минуты (закрытие рабочего GPU-движка на телефоне не проверялось — ревью У-11); несколько нажатий — сравнить `modelTotalMs` с GPU; вернуть «Видеоускоритель (GPU)».

20. (ревью У-1) Три нажатия подряд без смены дня: у 2-го и 3-го `conversation.mode` — `clone`, `conversation.base.at` одинаковый, `timing.turn.prefillTokens` — только звук и сообщение (около 25 на секунду записи плюс 15–20, а не +1050), ответы осмысленные, `timing.turn.decodeTokensPerSecond` не падает от нажатия к нажатию.

(`versionCode` 10, Р-39) Днём сказать «Сегодня в пять забрать машину» → «Добавлено: Забрать машину … — <сегодняшний день>», задача в сегодняшнем дне; в журнале `dateChoice`: если модель снова дала пятницу — `model` пятница, `chrono` и `saved` сегодня, `source: chrono`; если модель дала сегодня — `source: model`. «Завтра купить хлеб» и «послезавтра позвонить маме» → завтра и послезавтра. «В пятницу забрать машину» и «25-го оплатить интернет» → дата модели (`source: model`, даже если `chrono` другой). (`versionCode` 11, хвост записи) Сказать «Завтра обед в три часа дня» и отпустить кнопку сразу на последнем слове → кнопка сразу переходит в «обработку»; в журнале `thresholds.recordTailMs: 300`, `steps.tailMs` около 300, `recording.durationMs` ≈ `holdMs` + 300; WAV кончается тишиной, а не посреди слова; у задачи время 15:00.
