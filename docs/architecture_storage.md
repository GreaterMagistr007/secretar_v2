# Хранение данных

Формат хранения владелец поручил предложить самостоятельно (указание 2026-09-13). Критерии заданы им же: база со временем может стать очень большой, тормозить и создавать нагрузку она не должна; нужен поиск по вхождению в описание и индексация по дате — требования Т-6 (поиск по описанию), Т-7 (индексация по дате), Т-8 (производительность при росте базы).

Решение зафиксировано как Р-15 (хранилище IndexedDB через Dexie). **Реализовано 2026-09-15** в объёме таблицы `tasks`; отметки выполнения и повторения — следующим этапом. Код и проверки — [mechanic_tasks.md](mechanic_tasks.md).

## Выбор хранилища

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| **IndexedDB (через Dexie 4)** | асинхронный, индексы и диапазонные запросы, составные и multiEntry-индексы, сотни МБ, курсорная выдача | API многословный, поиска по подстроке нет из коробки | **выбран** |
| localStorage | простой | синхронный (блокирует UI), лимит ~5 МБ, индексов нет, всё парсится целиком | не годится под Т-8 |
| SQLite WASM + OPFS | настоящий SQL, `LIKE`, полнотекстовый FTS5 | +1–2 МБ wasm в бандл, сложнее сборка и отладка, в MVP избыточен | отклонён, кандидат при росте требований к поиску |

Dexie берётся ради типизированной схемы, миграций версий и курсоров; сам IndexedDB остаётся форматом хранения, так что уход от Dexie позже не ломает данные.

## Схема

### Таблица `tasks` — сама задача (правило, а не экземпляры)
| Поле | Тип | Назначение |
|---|---|---|
| `id` | string, PK | UUID v7 — сортируется по времени создания |
| `text` | string | текст задачи, требование Т-2 (обязательное) |
| `date` | string `YYYY-MM-DD` | дата задачи, для регулярной — дата старта правила, требование Т-3 |
| `priority` | `low` \| `medium` \| `high` | приоритет, требование Т-24 |
| `recurrence` | `none` \| `daily` \| `weekly` \| `monthly` \| `yearly` | регулярность, требование Т-4 |
| `searchTokens` | string[] | нормализованные токены текста под поиск |
| `createdAt` / `updatedAt` | number | epoch ms |

**Индексы (схема версии 1):** `date`, `priority`, `[priority+date]`, `*searchTokens` (multiEntry), `updatedAt`.

Поле названо `text`, а не `description`: так оно называется в контракте `src/lib/tasks/types.ts` и в интерфейсе. Индекс по `recurrence` в первой версии схемы не заводился — повторения ещё не реализованы, а индекс без запросов к нему только замедляет запись; он появится вместе с ними.

### Таблица `completions` — отметки выполнения по конкретным повторениям
**Ещё не реализована** (на 2026-09-15): статус выполнения, требование Т-5, идёт следующим этапом вместе с повторениями. Описание ниже — проект схемы.

| Поле | Тип | Назначение |
|---|---|---|
| `[taskId+occurrenceDate]` | составной PK | одна отметка на повторение |
| `taskId` | string | ссылка на задачу |
| `occurrenceDate` | string `YYYY-MM-DD` | день повторения, которое выполнено |
| `completedAt` | number | epoch ms |

**Индексы:** `taskId`, `occurrenceDate`.

Такое разделение — прямое следствие требования Т-5 (статус относится к конкретному повторению): отметка о выполнении принадлежит паре «задача + день», а не задаче. Для задачи без повторений повторение одно, его дата равна `date` задачи — ветвлений в коде не появляется.

## Почему база не распухнет
**Повторения не материализуются.** В хранилище лежит правило (одна строка в `tasks`), а вхождения в календарь вычисляются на лету для видимого диапазона дат. Ежедневная задача, заведённая один раз, не порождает 365 строк в год — она остаётся одной строкой. Растут только `completions`, и только по фактически отмеченным дням: сколько отметок поставил пользователь, столько и записей.

**Выборка дня или диапазона.** Сейчас, пока повторений нет, это один диапазонный запрос по индексу `date` между `from` и `to` — таблица целиком не сканируется, отклик не зависит от объёма базы (требование Т-8). Когда появятся повторения, добавятся ещё два запроса: регулярные задачи по индексу `recurrence` с разворотом правил в памяти и отметки по индексу `occurrenceDate`.

## Поиск по описанию (требование Т-6)
IndexedDB не умеет `LIKE '%…%'`, поэтому:
1. при сохранении задачи описание нормализуется (нижний регистр, `ё`→`е`, пунктуация в разделители) и раскладывается на токены — они кладутся в `searchTokens` с multiEntry-индексом;
2. поисковый запрос нормализуется так же и ищется по индексу **префиксом токена** (`startsWith`) — это индексный доступ, объём базы на скорость не влияет;
3. найденные кандидаты дополнительно проверяются точным вхождением подстроки в исходное описание — так выдача соответствует именно «вхождению», а не совпадению токена;
4. выдача ограничена и листается курсором; ввод в поиске дебаунсится.

**Граница подхода, названная явно:** запрос, начинающийся с середины слова («ажин» в «магазин»), по индексу не находится. Это осознанная цена: полноценный поиск по любой подстроке требует индекса 3-грамм, который раздувает базу в десятки раз, — при большой базе это противоречит требованию Т-8 (производительность при росте базы). Если владельцу понадобится поиск с середины слова, вариант «индекс 3-грамм» и вариант «SQLite WASM + FTS5» лежат в [backlog_post_mvp.md](backlog_post_mvp.md) с триггером возврата.

## Даты и часовой пояс
Дата хранится строкой `YYYY-MM-DD` как **плавающая** — без времени и без UTC-сдвига. Причина: задача «на 5 сентября» должна оставаться на 5 сентября при смене часового пояса и при переходе через полночь; хранение меток времени в UTC этот инвариант ломает. Строковый формат ещё и сортируется лексикографически, что делает диапазонные запросы по индексу прямыми.

## Правила повторения
- `daily` — каждый день начиная с `date`;
- `weekly` — тот же день недели;
- `monthly` — то же число месяца;
- `yearly` — то же число и месяц.
Даты окончания у правила в MVP нет.

**Отсутствующая дата** (31-е число в феврале, 29 февраля в невисокосном году) — предложение: повторение переносится на последний день месяца, чтобы задача не пропадала. Требует подтверждения владельца — вопрос В-8 (перенос повторения при отсутствующей дате).

**Правка задачи** меняет правило целиком и действует на все будущие повторения; ранее проставленные отметки в `completions` сохраняются. Причина: в MVP задача — одна сущность, истории версий правила нет, а терять отметки за прошлые дни хуже, чем оставить их.

**Удаление задачи** каскадно удаляет её отметки в `completions` — иначе остаются висячие записи, которые со временем разрастаются.
