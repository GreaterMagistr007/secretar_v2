# Технологический стек

Gate закрыт 2026-09-13 — решение Р-14 (стек: Vite + Svelte 5 + TypeScript). Вопрос В-2 (технологический стек) решён.

## Ограничения, из которых выбирался стек
- **PWA** — приложение смотрится на телефоне и обновляется без магазинов (требование Т-16).
- **Хостинг — GitHub Pages**: только статика, серверного рантайма и rewrite-правил нет.
- **Главная цель этапа — подобрать дизайн**: важна скорость итерации «правка → пуш → обновление на телефоне».
- **Данные на устройстве**, база может стать очень большой (требования Т-8, Т-9).
- **Минимальный MVP** (решение Р-3): зависимости берутся только под задачу, не «на вырост».

Node для сборки — **22 LTS**: Vite 8 требует `^20.19.0 || >=22.12.0`. На хосте разработки стоит Node 20.20.1 — формально подходит, но сборка ведётся в контейнере (решение Р-17), чтобы версия была одинаковой на всех устройствах.

## Отклонённые варианты
- **React** — тяжелее рантайм и больше кода на каждую перестановку в вёрстке; для проекта, где смысл этапа в переборе дизайна, это прямой минус. Экосистема компонентов, ради которой его обычно берут, при подборе собственного дизайна не нужна.
- **Vanilla TypeScript без фреймворка** — минус зависимость, но роутинг, реактивность и перерисовку списков пришлось бы писать руками; на трёх экранах с календарём это дороже, чем 4 КБ рантайма Svelte.
- **SvelteKit** — даёт маршрутизацию и SSR, но SSR на Pages не нужен, а adapter-static добавляет слой конфигурации ради того, что в трёх экранах решается хэш-роутером на несколько десятков строк.
- **Готовый UI-кит** (Material, Skeleton и подобные) — навязывает свой визуальный язык, что противоречит цели этапа «подобрать дизайн».

## Решения по реализации
- **Роутинг — хэш-based** (`#/calendar`, `#/task/:id`, `#/settings`), решение Р-19. Причина: GitHub Pages не умеет rewrite, и при обычных путях прямое открытие ссылки даёт 404. Свой роутер на несколько десятков строк, без зависимости.
- **`base` сборки** — `/secretar_v2/`: сайт живёт в подкаталоге репозитория, при `base: '/'` ассеты не найдутся.
- **Стили — обычный CSS** в компонентах Svelte, с CSS-переменными под тему. Причина: подбор дизайна идёт правкой значений, препроцессор и утилитарный фреймворк на этом этапе только добавляют слой.
- **Зависимостей в рантайме — минимум**: на первой поставке их нет вообще, кроме самого Svelte; Dexie появляется вместе с задачником.

## Окружение
Сборка и dev-сервер — в docker-контейнере (решение Р-17), образ `node:22-alpine`, запуск одной командой через `docker compose`. Node на хосте остаётся запасным путём. Подробности и команды — [deployment.md](deployment.md).

## Android: Capacitor
Android-приложение собирается из **той же** сборки: `dist/` кладётся в APK, работает в системном WebView, нативные возможности — через плагины (решение Р-20). Версия на 2026-09-13 — Capacitor 8.5.2. Выбор UI-фреймворка на этот переход не влияет: Capacitor от фреймворка не зависит. Нативный UI не делается — позиция каталога 20 остаётся не-целью.

Что это накладывает на код заранее:
- **Аутентификация токенами, не куками** (решение Р-23): origin приложения — `capacitor://localhost`, куки чужого домена там ограничены.
- **Вход через внешнего провайдера — системным браузером**, не встроенным WebView.
- **Хэш-роутинг** (решение Р-19) одинаково удобен и на Pages, и в Capacitor, где страница открывается с локальной схемы.
- **Идентификаторы задач генерирует клиент** (UUID v7), иначе созданная офлайн задача не имеет имени до выхода в сеть.

## Серверная часть (решение Р-22)
Появится после прототипа: авторизация, сессии, данные пользователей в серверной базе; клиентская база остаётся офлайн-копией с синхронизацией. Язык сервера — **TypeScript**: типы сущностей, схемы валидации и правила синхронизации описываются один раз и переиспользуются клиентом и сервером. Конкретный серверный фреймворк и движок синхронизации выбираются при переходе к этому этапу — позиции каталога 17 и 24.
